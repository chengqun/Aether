# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Build, test, run

Single solution: `Aether.AI.Platform.slnx` (note: `.slnx`, not `.sln`). .NET 10.

```bash
# git submodules — init before first build (shallow, pinned to a fixed commit)
git submodule update --init externals/Lean externals/FlaUI-MCP   # Lean = futures engine; FlaUI-MCP = Windows desktop-control MCP server (optional, Windows-only)

dotnet build Aether.AI.Platform.slnx          # build everything
dotnet test  Aether.AI.Platform.slnx          # run all test projects

# Single project build/test (dotnet build/test accept ONLY ONE project in this env)
dotnet test tests/Aether.AI.Harness.Tests/Aether.AI.Harness.Tests.csproj --filter "FullyQualifiedName~Memory"

# Run the desktop app (Avalonia; Stockapp tenant with CTP/Quotes/Trading; Qifu tenant with Yushu/CloudDocs)
dotnet run --project apps/Stockapp/Acme.Stockapp.Desktop
dotnet run --project apps/Qifu/Acme.Qifu.Desktop
```

The first build after init is slow (Lean source compiles). Lean's transitive deps emit NU1902/3/4 vulnerability advisories (System.Drawing.Common / WCF / WinHttpHandler) — advisory only, expected.

## Big-picture architecture

A multi-context DDD platform built on **Microsoft Agent Framework** (`Microsoft.Agents.AI`, wrapped by `src/Aether.AI.Harness`). Top-level layout enforces a strict layering:

- `src/` — the **Aether.AI platform** itself, standalone. `Aether.AI.Abstractions` (zero-ProjectReference contract package — MCP contract types `McpServerConfig`/`IMcpServerRegistry`/`McpServerEntry`/`McpToolInfo`/`McpServerStatus`/`IMcpManagementService`; one stable PackageReference `Microsoft.Extensions.AI.Abstractions` for `AIFunction`; the **only** `Aether.AI.*` project `business/` may reference — `Acme.AppAutomation.McpClient` consumes `IMcpServerRegistry`/`McpServerConfig` from here), `Aether.AI.Core` (framework-agnostic domain, zero deps), `Aether.AI.Harness` (AgentFactory/HarnessRuntime/SessionManager/ToolRegistry/SkillRegistry/IChatClientFactory wrapping MEAI), `Aether.AI.Workflows` (WorkflowFactory wrapping MAF Workflows — peer of Harness, does NOT depend on Harness), `Aether.AI.Memory` (IConversationStore abstraction + InMemory impl), `Aether.AI.Memory.Sqlite` (SQLite impl, opt-in), `Aether.AI.Hosting` (`services.AddAetherAI()` DI entry point + DefaultChatClientFactory + ConversationTitleService). Platform source never references `business/` or `ai/`.
- `business/` — **pure DDD bounded contexts**, each `Acme.<Context>.{Domain,Application,Infrastructure}`. AI-free.
- `ai/` — **business AI adapters** bridging Aether and each context. Peers of `business/`, kept separate so business stays AI-free. 7 tool adapters (`Ctp/Quotes/Qifu/Notes/Trading/ApkParser/SystemTools`) + 1 agent bridge (`Agents`). Not every context has an AI adapter — e.g. Automation has none (its business port `IAgentExecutor` is implemented host-side; see [business-port pattern](#business-domain-port--host-implementation) below). The **agent bridge** `ai/Agents/Acme.Agents.AI` is NOT a tool adapter — it registers `ICustomAgentCatalog`/`ICustomAgentRunner` (CRUD + run-time for custom agents), not tools. It is the only adapter that doesn't follow the "register tools only" convention, by design.
- `externals/` — third-party engines: `Ctp.Net.Core` (native CTP wrapper), `Lean` (QuantConnect Lean, git submodule), and `FlaUI-MCP` (Windows desktop-control MCP server, git submodule; consumed by the [AppAutomation](#appautomation-context-桌面控制--固定过程) MCP path).
- `apps/` — consumers/hosts: `Acme.Shell` (UI-agnostic shell VM library), `Desktop/Acme.Desktop.Shared` (Avalonia views + composition root), `Qifu/Acme.Qifu.Desktop` + `Stockapp/Acme.Stockapp.Desktop` (tenant host apps). (Qifu 不在 slnx 注册——Stockapp 同步 GitHub 时 Qifu 隐藏。)
- `tests/` — all test projects live here, never interleaved with source.

### DDD layering rules (enforced; verify before changing csprojs)

- **Domain** = pure: zero `ProjectReference`, no SDK/HTTP/SQLite/logging packages, no `Aether.AI.*`. Entities/value-objects/ports only. A Domain may reference another context's Domain (shared kernel) — e.g. 8 contexts reference `Acme.AppAuth.Domain`.
- **Application** → Domain (+ foreign Domain port). Never Infrastructure/AI/externals.
- **Infrastructure** → Domain (+ externals + foreign Domain contract). Never another context's Infrastructure.
- **`business/` must NEVER reference `Aether.AI.*`.**
- Dependency graph is a DAG; no cycles. `Acme.AppAuth.Domain` is the pure source (foundation), `Acme.Trading.Runtime.Lean` the pure sink.

### AI adapter convention (`ai/<Context>/Acme.<Context>.AI`)

Every **tool adapter** is the same shape (mirror `ai/Ctp`):
- csproj: `Aether.AI.Hosting` + the context's **Application** project (never Infrastructure/Domain directly).
- `AddXxxTools(this AetherAIBuilder)` registers tools ONLY — there is **no** `AddXxx(modelId)` agent method. Agents are built dynamically by the host/page from the shared tool pool. `ToolNames[]` + `CreateTool<T>` helper using `AIFunctionFactory.Create`.
- Tool classes live in `Tools/`, namespace `Acme.<Context>.AI.Tools`. Tools call Application contracts, never Domain/Infrastructure.
- `AddXxxTools` registers TOOLS ONLY — the host composition root wires business layers.
- **例外：`ai/Quotes/Acme.Quotes.AI`** 是跨上下文工具适配器——引 `Securities.Application`（`SecurityQueryTool` 用 `ISecurityService` 查证券）+ 在 `AddQuotesTools` 注册 `ISecurityLookup` ACL 适配器（`SecurityLookupAdapter` 桥接 `ISecurityManager`→`ISecurityLookup`，让 Quotes 不直接依赖 Securities）。因 Quotes 工具需 Securities 数据，ACL 桥接是设计决策。`ai/Trading/Acme.Trading.AI` 引 `Trading.Scripting`（`CreateStrategyTool` 用 `StrategyScriptCompiler` 即时编译验证）——同理例外。

The **bridge adapter** `ai/Agents/Acme.Agents.AI` is a different shape:
- References `Aether.AI.Hosting` + `Acme.Notes.Application` (custom agents persisted as Notes) + `Acme.AppAuth.Application` (for `IAppServerHttpClient`, marketplace client).
- `AddCustomAgents(this AetherAIBuilder)` registers `ICustomAgentCatalog` (CRUD over Notes-backed agents via `AgentSourceParser`), `ICustomAgentRunner` (maps `CustomAgentDefinition` → `AgentDefinition` → `HarnessRuntime`), `IAgentMarketplaceService` (cloud agent catalog client).
- `AddCustomWorkflows(this AetherAIBuilder)` registers `ICustomWorkflowCatalog` (CRUD over Notes-backed workflows via `WorkflowSourceParser` — JSON, not YAML) + `ICustomWorkflowRunner` (builds participants via `AgentFactory`, wraps as MAF Handoff workflow via `WorkflowFactory.BuildAsAIAgent`, runs through `HarnessRuntime.RunStreamingAsync(AIAgent,…)` — reuses the same `RunStreamingCoreAsync` extraction loop as agents). Workflow persistence: `WorkflowSourceParser` (JSON content, `NoteNodeType.Workflow`) in `business/Notes/Acme.Notes.Infrastructure/Agents/`. Fields: name/description/category/entry_agent_id/participants/handoffs/handoff_instructions.
- Custom agent persistence: `AgentSourceParser` (YAML front-matter + Markdown prompt) in `business/Notes/Acme.Notes.Infrastructure/Agents/`. Fields: name/description/category/tools/skills/memory/max_history/model/top_p/max_output_tokens/response_format/enable_web_search/enable_todo_provider/enable_agent_mode_provider/enable_file_memory/enable_agent_skills/enable_open_telemetry/source/marketplace_id/marketplace_synced_at/display_name. `Serialize(CustomAgentDefinition)` takes the definition directly. Business layer defines its own `AgentMemoryMode`/`AgentResponseFormat` enums (parallel to Core's) — adapter maps them, so `Aether.AI.*` never leaks into Notes.

### Business Domain port → host implementation

When **business logic must trigger agent execution** (or anything AI/platform-specific) but business cannot reference `Aether.AI.*`, define a **port interface in the context's Domain** and implement it **in the host composition root**. This is the canonical pattern — do NOT create an `ai/` adapter just to host a port impl, and do NOT make business depend on AI.

- **Port** in `Acme.<Context>.Domain.Interfaces` (e.g. `IAgentExecutor`). Domain stays pure; the Infrastructure service/scheduler depends on the port, not on AI types.
- **Implementation** lives in an AI-aware host project (`apps/Acme.Shell` or `apps/Desktop/...`), depending on platform/AI types (`ICustomAgentRunner`, `IConversationStore`, …), NEVER on business Infrastructure.
- **Registration** at the composition root (`AddDesktopCommon`): `services.AddSingleton<IPort, HostImpl>()`.
- **Reuse, don't re-route**: the impl should call the *same* runtime path the UI uses, not a parallel one. Canonical example — `ConversationBackedAgentExecutor` (`apps/Acme.Shell`): Automation's scheduler calls `IAgentExecutor.ExecuteAsync`; the impl runs the agent via `ICustomAgentRunner.RunStreamingAsync` and persists the turn to `IConversationStore`, so scheduled runs land in「最近会话」with cross-fire memory — identical to the chat page's flow. Each task owns a stable `ConversationId` (stored on the entity) so fires thread into one conversation.
- The business layer raises completion via a port event (`IAutomationScheduler.TaskCompleted`); the host VM subscribes and refreshes UI (task list + recent conversations) on the dispatcher thread.

Reference: Automation is the working template — `business/Automation/` (Domain port + scheduler) + `apps/Acme.Shell/ConversationBackedAgentExecutor.cs` (host impl) + `AddDesktopCommon` (registration).

### Foundation context

`business/AppAuth/` (`Acme.AppAuth.*`, DI classes named `Platform*Extensions`) is the **foundation**: app-server (ABP) OAuth2 auth + authenticated HTTP (`IAppServerHttpClient` with `TenantHeaderDelegatingHandler` + `BearerTokenDelegatingHandler`) + `ICurrentUser`. Other contexts consume its ports — never the reverse.

### Trading + Lean (the engine-bridge pattern)

The 回测/实盘 page, the business Trading context, and the Lean runtime are **four separated layers** with a one-way dependency. The UI and business layers never reference Lean — swapping the runtime is a DI-only change.

```
Desktop 回测/实盘页  (TradingViewModel + TradingView, apps/Stockapp)   ← runtime-agnostic
        ↓ depends on
Trading.Application  (IBacktestApplicationService / ILiveTradingApplicationService)   ← orchestration, Lean-neutral
        ↓ depends on
Trading.Runtime.Domain  (ports: IBacktestRuntime / ILiveTradingRuntime; BarResolution; LiveTradingRuntimeStatus; MarketDataConnectInput)
        ↑ implemented by
Trading.Runtime.Lean  (LeanBacktestRunner / LeanLiveTradingService / CtpBrokerage / TradingHostAlgorithm)   ← the ONLY project referencing externals/Lean
        ↓ consumes (DI-provided, not self-registered): ICtpSession (Ctp context) + IAnalysisManager (Quotes context)

Trading.Domain  (IStrategy / MarketBar / SignalDirection / BacktestResult / BacktestStatistics / EquityPoint / StrategyRegistry)   ← pure, shared by Application + Lean
```

- **`business/Trading/Acme.Trading.Domain`** — pure: `IStrategy` (`WarmUpBars`/`Initialize`/`EvaluateSignal→SignalDirection` + `ParameterDefinitions` 接口默认返回空，策略可选覆盖声明参数供 UI 动态渲染), `StrategyParameterDef` (`Key`/`Label`/`DefaultValue`), `MarketBar`, `BacktestResult` (`Statistics`/`EquityCurve`/`Logs`), `StrategyRegistry` (static; `Register`/`Unregister`/`Create`/`GetRegisteredNames()`/`GetParameterDefinitions(name)` feeds the UI strategy picker + 参数 UI). 内置策略已删——全部走动态加载。
- **`business/Trading/Acme.Trading.Application`** — `IBacktestApplicationService.RunAsync(BacktestRunInput)→BacktestResult` and `ILiveTradingApplicationService` (`StartAsync(LiveTradingRunInput)→(bool,string?)`, `StopAsync`, `Status`/`IsRunning`, `StatusChanged`/`LogReceived` events). Thin mappers to the runtime ports. `AddTradingApplication()` registers both.
- **`business/Trading.Runtime/Acme.Trading.Runtime.Domain`** — the runtime **ports** (`IBacktestRuntime`, `ILiveTradingRuntime`) + shared enums/DTOs. No Lean.
- **`business/Trading.Runtime/Acme.Trading.Runtime.Lean`** — the **only** project referencing `externals/Lean`. `LeanBacktestRunner` (full backtest: reads K-line via `IAnalysisManager` → CSV → LEAN engine → `BacktestResult`). `LeanLiveTradingService` (LEAN live engine + `CtpBrokerage`). `AddTradingRuntimeLean()` registers both runtime impls (不再注册内置策略——策略由 Scripting 动态加载); it **consumes** (does not register) `ICtpSession` (from `AddCtpInfrastructure`) and `IAnalysisManager` (from `AddQuotesApplication`).
- **`business/Trading.Runtime/Acme.Trading.Scripting`** — 策略动态加载：经 `IStrategyNoteSource` 端口（`Trading.Runtime.Domain`）读策略笔记，按 `StrategyNote.Kind` 分发——`Code`（Roslyn 动态编译 `IStrategy` 实现类源码）/ `Yaml`（`StrategyProgramYaml` 解析声明式配方 → `YamlStrategy`）→ `StrategyRegistry.Register`。host（Stockapp `StrategyNoteSource`）桥接 `INoteService`，按 `NodeType is CodeStrategy or Strategy` 过滤并映射 `Kind`（CodeStrategy→Code，Strategy→Yaml）——此处是唯一知 NoteNodeType 语义的地方，Trading.Scripting 本身 Notes 无关。`IStrategyScriptingService.LoadAsync()`/`Reload()` + `StrategiesLoaded` 事件（UI 刷新选择器）；订阅 `NotesChanged` → `Reload()` 自动重编译。`Trading.AI` 引用此项目（`CreateStrategyTool` 用 `StrategyScriptCompiler` 即时编译验证；工具创建笔记时设 `NodeType=CodeStrategy`——修前误用 `Note`+`Tags=strategy` 导致不被 `StrategyNoteSource` 加载）——AI 适配器引非 Application business 项目的例外，因编译验证需要。
- **Desktop 回测/实盘页** (`apps/Stockapp/.../ViewModels/TradingViewModel.cs` + `Views/TradingView.axaml`, the `backtest` nav): 回测和实盘**合并为单页**，顶部模式 RadioButton（回测/实盘）切换配置区。子 TabControl（⚙ 配置 / 🎯 策略 / 📈 统计 / 📊 曲线 / 📋 日志）。策略 tab 含策略选择 ComboBox（回测/实盘各自绑 `StrategyName`/`LiveStrategy`）+ 策略参数动态渲染（`StrategyParameterRows`，从 `StrategyRegistry.GetParameterDefinitions` 加载）。配置 tab 含合约/日期/资金/分辨率（回测）/CTP 前置+详细日志（实盘）。日志 tab 按模式显示回测 `LogText` 或实盘 `LiveLog`。互斥守卫（`CanRun`/`CanStartLive` 互相检查）。The VM depends on `Trading.Application` + `Trading.Runtime.Domain` enums + `Trading.Domain` only — **never** on `Trading.Runtime.Lean`.
- **AI** (`ai/Trading/Acme.Trading.AI`): `AddTradingTools()` exposes `RunBacktest` + `CreateStrategy`（创建策略笔记 + 即时编译验证，`Confirm` 级）.

Runtime paths:
- **Backtest**: `TradingViewModel.RunCommand` → `Task.Run(() => _backtest.RunAsync(input))` (blocking, so off the UI thread) → `BacktestResult` (12 string stats + `EquityCurve` + `Logs`). **Data caveat**: K-line comes from `IAnalysisManager` (Quotes context, stock-oriented Sina/East/Baidu providers) — futures symbols may have no data; stocks (e.g. `600000`) work.
- **Live**: `StartLiveCommand` → `_live.StartAsync(LiveTradingRunInput)`; preconditions: `ICtpSession` already logged in (CTP connected via the 期货 page) + a complete `MarketDataConnectInput` (md front, built from `CtpConnectorViewModel`). Subscribe to `StatusChanged`/`LogReceived` (dispatch to UI thread). **P1 = signal-only**: `CtpBrokerage.PlaceOrder` logs the intended order and returns `false` — no real CTP order is placed; the tick→bar→signal chain is live. 停止：`Schedule.On(Every 2s)` 检查 `TradingGateway.StopRequested` → `Quit`（无 tick 时 OnData 不调，需 Schedule 兜底）。`AlgorithmStatus.Stopped` 算正常退出（不是 Error）。
- **CtpBar.GetSource**（回测 vs 实盘数据路径的关键设计决策）：回测（`isLiveMode=false`）返回 `LocalFile`（Lean `ShouldStreamSubscription=false` → 走 DataProvider 读 CSV）；实盘（`isLiveMode=true`）返回 `Streaming`（`ShouldStreamSubscription=true` → 走 `IDataQueueHandler.Subscribe` → `CtpBrokerage`）。之前实盘返回 `LocalFile` 导致 `CtpBrokerage.Subscribe` 没被 Lean 调 → `_symbolByInstrument` 空 → tick 全被过滤 → 算法收不到数据。
- **CtpSessionService 增量订阅**：`SubscribeMarketDataAsync` 已连接+同账户时不重建连接，只 `_md.SubscribeMarketDataAsync(新symbols)` 增量累加（native CTP md 支持累加订阅）。之前每次调都 Dispose 旧 _md + new → 实盘订阅覆盖期货页全量。`CtpBrokerage.EnsureCtpMdSubscribed` 不跳过 `_session.IsMdSubscribed`（总是调，CtpSessionService 增量处理）。
- **Lean Config 全局静态 gotcha**：回测和实盘在同进程共享 Lean 的 `Config`/`Globals`/`Composer`（全局静态）。实盘跑后回测需在 `ConfigureLean` 显式覆盖 `live-mode=false` + `Globals.Reset()` + 清 live 残留（`live-mode-brokerage=""`/`data-queue-handler=""`/`data-feed-handler=FileSystemDataFeed`）。互斥守卫防同时跑。
- **P2 (real orders, future) — no new dependency, no cycle.** `CtpBrokerage` already injects `ICtpSession` (uses it for md subscribe / account query / `OrderReceived`+`TradeReceived` events). P2 just makes `PlaceOrder` call `_session.OrderInsertAsync(CtpOrderRequest)` (Lean Order → `CtpOrderRequest` mapping) and translates the already-subscribed `OrderReceived`/`TradeReceived` back into Lean Order/Trade events. This reuses the **same `ICtpSession.OrderInsertAsync`** port the 期货 page manual trading uses (`ICtpTradingService.PlaceOrderAsync`) — two consumers, one port. The edge `Trading.Runtime.Lean → Ctp.Domain` already exists; `Ctp.*` never references `Trading.*`, so there is no cycle. `CtpBrokerage` must stay in `Trading.Runtime.Lean` (it subclasses Lean's `Brokerage`); Ctp stays Lean-free.
- **Swapping the runtime** (Lean→other): implement `IBacktestRuntime`/`ILiveTradingRuntime` in a new project and replace the `AddTradingRuntimeLean()` registration. `Trading.Application`, `Trading.Domain`, and the desktop VM are untouched.

### Tenant-specific top-level pages (ContentControl + DataTemplate)

Some nav pages are tenant-specific (Stockapp's 期货 page uses CTP; its 回测/实盘 page uses Trading/Lean; its 股票 page uses StockTrading/FlaUI; Qifu has none). The shared shell must not reference tenant/CTP/Trading types. Pattern:
- Shared `MainViewModelBase` exposes an `object?` content slot + an `IsXxxPage` flag — `Futures`/`IsFuturesPage => CurrentPage == "ctp"`, `Trading`/`IsTradingPage => CurrentPage == "backtest"`, `StockTrade`/`IsStockTradePage => CurrentPage == "stocktrade"`.
- Shared `MainWindow.axaml` renders each via `<ContentControl Content="{Binding ...}" IsVisible="{Binding Is...Page}" />`.
- The tenant VM+View live in the **tenant project** (`apps/Stockapp/.../ViewModels` + `Views`); the tenant `App.axaml` registers `<Application.DataTemplates>` mappings (e.g. `CtpViewModel→FuturesView`, `TradingViewModel→TradingView`, `StockTradingViewModel→StockTradingView`) and the tenant `MainViewModel` assigns the VM to the slot (`Futures = ctpVm; Trading = tradingVm; StockTrade = stockTradingVm;`). Qifu leaves them null (no nav entries, flags stay false).
- The tenant VM depends only on Application-layer services (e.g. `ICtpTradingService`, `IBacktestApplicationService`, `IStockTradingApplicationService`) + the shared connector, never on `externals/Ctp.Net.Core` or `Trading.Runtime.Lean` directly.

### StockTrading context (A股 GUI 自动化下单; distinct from Trading/Lean)

`business/StockTrading` (`Acme.StockTrading.{Domain,Application,Infrastructure}`) is a **separate** context from `business/Trading` (futures backtest/live via Lean). It trades A-shares by **driving the 同花顺 (THS) order client GUI via FlaUI** — NOT an exchange API. Port `IStockBrokerage` (`Domain`, OS/GUI-agnostic: Connect/LaunchClient/PlaceOrder/Cancel/QueryPositions + `IsConnected`/`LogReceived`); `StockTradingApplicationService` (thin proxy) → `IStockTradingApplicationService` (the UI/AI contract). `AddStockTradingApplication()` (cross-platform) + `AddStockTradingFlaUi(opts)` (Windows-only Infrastructure) are the DI entry points.

- **Windows-only Infrastructure**: `Acme.StockTrading.Infrastructure` is `net10.0-windows` + `UseWPF` (FlaUI needs Windows UIAutomation; reading the THS positions grid uses `System.Windows.Clipboard`). Domain/Application stay pure `net10.0`.
- **Avalonia MTA-vs-STA handled**: Avalonia UI thread is MTA; FlaUI/Clipboard need STA. `FlaUiStockBrokerage.RunSta` marshals each op to an STA background thread, so the Avalonia host is fine. csproj `CopyFlaUiDependenciesToOutput` target copies FlaUI transitively-deps into bin (lib projects don't by default).
- **Config port (`IStockTradingOptions` in Domain, peer of `IStockBrokerage`)**: OS-agnostic getter/setter for `ClientExecutablePath`/`ClientWindowTitle`/`StepDelayMs` — lets the UI read/write THS config without depending on the Windows-only `FlaUiStockBrokerageOptions` (Infrastructure). Impl: `FlaUiStockBrokerageOptionsAdapter` (Infrastructure, forwards to the `FlaUiStockBrokerageOptions` DI singleton). **改字段即时生效** — `FlaUiStockBrokerage` holds the same options reference and re-reads per op (no restart needed). Registered in `AddStockTradingFlaUi()` (Windows) / `UnsupportedStockTradingOptions` stub (non-Windows, fields rw but unconsumed). `FlaUiStockBrokerageOptions` defaults: `ClientExecutablePath=null` (attach-only to a running window), `ClientWindowTitle="网上股票交易系统5.0"`, `StepDelayMs=100`.
- **Multi-target host (Stockapp)**: `Acme.Stockapp.Desktop` `TargetFrameworks` is **OS-conditional** — `$([MSBuild]::IsOSPlatform('Windows'))` → `net10.0-windows;net10.0`; otherwise → `net10.0` only. Reason: NuGet restore of a multi-target project evaluates **all** TFMs, so even `dotnet build -f net10.0` would evaluate `net10.0-windows`, pulling in `StockTrading.Infrastructure` (net10.0-windows + UseWPF) → NETSDK1100 on macOS; declaring only `net10.0` on non-Windows keeps the windows TFM out of restore entirely. The Infrastructure `ProjectReference` is `Condition="'$(TargetFramework)' == 'net10.0-windows'"`; `DefineConstants;WINDOWS` marks the windows build. In `App.axaml.cs`, `#if WINDOWS` → `AddStockTradingFlaUi()`; `#else` → register `UnsupportedStockBrokerage` (ops return "仅支持 Windows") + `UnsupportedStockTradingOptions` stubs so the 股票 page + 连接器 still resolve/open on macOS but are inert. Publish must pass `-f` (NETSDK1129: 复数 `TargetFrameworks` 属性即便单值也按跨目标处理) — Windows scripts `-f net10.0-windows`, mac/linux scripts `-f net10.0` (the mac/linux/`build-desktop-macos.sh` scripts all do). **`StockTrading.Infrastructure.csproj` itself is always `net10.0-windows`** (FlaUI/WPF can't downgrade); to let the IDE + `dotnet build Aether.AI.Platform.slnx` load it on non-Windows, it sets `EnableWindowsTargeting=true` Condition `!IsOSPlatform('Windows')` (WindowsDesktop 引用程序集评估；mac 上 Stockapp 走 net10.0 不引用它，这份 windows DLL 不被消费).
- **Connector (data-driven cards, shared template)**: the Experts「连接器」tab renders an `ItemsControl` bound to `IConnectorViewModel.Cards` with a `WrapPanel` ItemsPanel + a **shared inline card DataTemplate** in `ExpertsView.axaml` (the only card XAML for connectors). `IConnectorViewModel` (shared shell) now exposes `IReadOnlyList<ConnectorCardViewModel> Cards` (+ `RefreshAsync`); each card derives from `ConnectorCardViewModel` (Icon/IconBackground/Title/Description/IsConnected/StatusText/IsPrimaryEnabled/ShowSync + `PrimaryCommand`/`SyncCommand` + abstract `RefreshAsync`). Adding a connector = add a `ConnectorCardViewModel` to `Cards` — **zero XAML change, auto-wraps**. ### AppAutomation context (桌面控制 / 固定过程)

`business/AppAutomation` (`Acme.AppAutomation.{Domain,Application,Infrastructure,StockTradingBridge,McpClient}` — 5 projects, not the usual 3) is the **desktop GUI control** context. It sinks OS-specific GUI automation (FlaUI on Windows, AX/osascript on Mac — future) **out of the Aether process into an out-of-process MCP server** (`externals/FlaUI-MCP`), so Aether upper layers call it via the standard MCP protocol and platform differences = a different `mcp-servers/desktop.json`. Two paths share one MCP server:

- **① 固定过程 (fixed procedures)** — `IProcedureRunner.RunAsync(name, args)` runs a **code-codified UI flow** (deterministic,适合精确/不可逆动作如下单). This is the AppAutomation context's own path.
- **② LLM 直连 (direct)** — an agent calls the desktop MCP server's tools directly (Click/Type/GetUITree) via the existing `McpServerRegistry` (`Aether.AI.Mcp`); the sequence is decided by the LLM at runtime. **Does NOT go through `IDesktopAutomation`.**

> 两条路径在 **server 端**共用同一组工具，但在 **Aether 上层**走**两套独立、互不相连**的客户端 seam：② 用 `McpServerRegistry`（既有 MCP client），① 用 AppAutomation 自己的 `IMcpToolInvoker` 端口。配一份 `desktop.json` 两条都通的前提是 ① 有真实 `IMcpToolInvoker` 实现（`RegistryMcpToolInvoker` 复用 `IMcpServerRegistry` 已连的 desktop server 工具——与专家页 MCP tab 同源，零重复连接）。

Ports (`Acme.AppAutomation.Domain`): `IProcedureRunner` (run a named procedure), `IDesktopAutomation` (C# primitives: Click/Type/GetUITree/FindElement/WaitForElement/GetText…, **只服务于①固定过程**), `IMcpToolInvoker` (CallToolAsync/IsConnected — the seam between AppAutomation and the MCP server; AppAutomation does **not** reference `Aether.AI.Mcp`).

Projects:
- **Application** — `Procedure` (abstract: name + RunAsync(primitives,args)) / `ProcedureCatalog` (name→Procedure) / `ProcedureRunner`. `Ths*Procedure` (ThsConnect/Launch/PlaceOrder/Cancel/QueryPositions/Disconnect) live in Infrastructure (locator-anchored). **DI gotcha**: `AddAppAutomation()` registers each procedure as `Singleton<Procedure>`, but DI only resolves them when `ProcedureRunner` injects `IEnumerable<Procedure>` — its ctor self-registers them into `ProcedureCatalog`. Without that injection the catalog stays empty → `RunAsync` reports「未知固定过程」.
- **Infrastructure** — `McpDesktopAutomation : IDesktopAutomation` (locator↔FlaUI-MCP ref mapping layer: `windows_snapshot` finds ref → `windows_click`/`windows_type`/`windows_get_text`; `FindRefInTree`/`ToChord` pure fns, unit-tested without a server) + `NotConnectedMcpToolInvoker` (Mac/未配 server 桩: `IsConnected=>false`, `CallToolAsync=>"{}"` — 优雅失败「桌面控制后端未连接」, 不崩) + `AddAppAutomation()` DI.
- **McpClient** — `RegistryMcpToolInvoker : IMcpToolInvoker` (复用 `IMcpServerRegistry` 已连的 desktop server, 按工具名从 `GetTools()` 找 `AIFunction` 调 `InvokeAsync`) + `McpDesktopToolInvoker` (独立连备选, 未启用). 隔离 `ModelContextProtocol` alpha 包. **引用 `Aether.AI.Abstractions`**（取 `IMcpServerRegistry`/`McpServerConfig` 稳定契约，零 alpha 依赖）——是 `business/` 引 `Aether.AI.*` 的唯一合法出口（Hosting 的 MCP 契约已上移到 Abstractions，消除原 McpClient→Hosting 的层化违规）.
- **StockTradingBridge** — `AppAutomationStockBrokerage : IStockBrokerage` (maps the StockTrading port → `IProcedureRunner`: Connect/Launch/PlaceOrder/Cancel/QueryPositions → procedures) + `ThsPositionsParser` (持仓 Tab 文本 → `StockPosition[]`). 独立项目, 引 `StockTrading.Domain`（外域契约）+ `AppAutomation.Application`; StockTrading 真正零改动.

**Stockapp host wiring** (`App.axaml.cs`, business-port → host impl pattern, 类比 `IAgentExecutor`): `RoutingStockBrokerage` (host, `apps/Stockapp/.../Hosting/`) is the default `IStockBrokerage` — keyed services hold two backends (`"flaui"` = `FlaUiStockBrokerage`, `"mcp"` = `AppAutomationStockBrokerage`), runtime-switchable via the 股票页 FlaUI/MCP RadioButton (`OrderMethod` enum, persisted `stocktrade.method`); `Active` delegates to the selected backend. Stockapp registers `AddAppAutomation()` + `RegistryMcpToolInvoker` → keyed `"mcp"` `IStockBrokerage` = `AppAutomationStockBrokerage(IProcedureRunner)` + `RoutingStockBrokerage` as default. Non-Windows / no desktop server → `IsConnected` 恒 false, `ProcedureRunner` 优雅失败. The MCP server config template lives at `apps/Stockapp/.../mcp-servers/desktop.json` (copy to tenant dir to enable). **本期不删 FlaUI 多目标**——MCP 路线完全验证通过、决定取代 FlaUI 后才退回单一 `net10.0`（可选后续）.

### Per-agent model + memory (platform layer)

- **Per-agent ModelId**: `AgentDefinition.ModelId` (opaque string) resolved by `IChatClientFactory.Create(modelId)` → `IChatClient`. Platform default (`DefaultChatClientFactory`): uses `AetherAIOptions.OpenAI` key/endpoint. Desktop override (`DesktopChatClientFactory`): maps ModelId = LlmConfig.Id → builds per-provider client.
- **Memory policy**: `AgentDefinition.Memory` (`Full`/`SlidingWindow`/`Off`) + `MaxHistory`. Enforced at agent build time via `HarnessAgentOptions.ChatHistoryProvider`: Full→null (default InMemory), SlidingWindow→`InMemoryChatHistoryProvider` + `SlidingWindowChatReducer`, Off→`NoMemoryChatHistoryProvider`.
- **Extended agent options**: `AgentDefinition` also carries sampling (`TopP`/`MaxOutputTokens`/`ResponseFormat`), HarnessAgent provider toggles (`EnableWebSearch`/`EnableTodoProvider`/`EnableAgentModeProvider`/`EnableFileMemory`/`EnableOpenTelemetry`), `EnableLongTermMemory` (cross-session memory, see [Agent 扩展能力](#agent-扩展能力tools--mcp--skill--长期记忆)), `RequireToolApproval` (per-agent tool-approval master toggle, see [Chat streaming surface](#chat-streaming-surface-reasoning--approval--plan--mode--ask_user)), `ToolApprovals` (per-tool level override `name→"Safe"/"Confirm"/"Dangerous"`), and `Skills` (name list). All mapped in `AgentFactory` (Core enums → MEAI; `ResponseFormat` via a Core `AgentResponseFormat` so MEAI types never leak into Core). Provider toggles default off (lightweight runtime); `EnableFileMemory` only takes effect when `AetherAIOptions.FileMemoryRoot` is set. MCP tools are NOT a flag — they flow through `ToolRegistry` (registered at startup) and are selected per-expert in the editor's MCP section.
- **`AetherAIOptions` paths**: `FileMemoryRoot` (writable root for the file-memory provider; null → silently disabled), `SkillsDirectory`, `PythonExecutable`. Set by the desktop composition root to tenant-data subdirs.
- `HarnessRuntime.Invalidate(agentId)` drops cached agent + definition (on edit).
- **Streaming core reuse**: `HarnessRuntime.RunStreamingCoreAsync` (private static) holds the shared streaming loop. It dispatches every `AIContent` kind in the stream to a `StreamHandlers` callback bundle (Core, framework-agnostic): `OnToken` (answer `TextContent`/`update.Text`), `OnReasoning` (`TextReasoningContent`), `OnToolEvent` (`FunctionCallContent`/`FunctionResultContent` → `ToolStreamEvent`), `OnApprovalRequest` (`ToolApprovalRequestContent`), `OnTodoList` (live `TodoProvider` list after `todos_*`), `OnError` (`ErrorContent`), `OnUsage` (`UsageContent` → token summary). Called by both `RunStreamingAsync(Guid sessionId,…)` (agent path, with AetherSession bookkeeping) and `RunStreamingAsync(AIAgent, FrameworkAgentSession,…)` (workflow path, no bookkeeping). This is how workflows reuse the same display pipeline as agents. See [Chat streaming surface](#chat-streaming-surface-reasoning--approval--plan--mode--ask_user).
- **Workflows** (multi-agent Handoff): `Aether.AI.Workflows` project (peer of Harness, only depends on Core + MAF Workflows NuGet). `WorkflowFactory.BuildAsAIAgent(def, participants, id, name, desc)` → `HandoffWorkflowBuilder` → `.Build()` → `AsAIAgent(InProcessExecution.Default)` → `AIAgent`. The adapter (`CustomWorkflowRunner`) builds participants via `AgentFactory.Create` (same factory as single agents) + maps `CustomAgentDefinition`→`AgentDefinition` via `CustomAgentRunner.ToAgentDefinition` (internal). Chat dispatch: `MainViewModelBase.SelectedWorkflow` (non-null → workflow path; null → agent path), both through the same `RunSegmentedStreamAsync` (run delegate).

### Skills (prompt + Python-script capabilities)

Skills are prompt-based capabilities (Agent Skills spec — same `SKILL.md` format as Claude Code) loaded from a directory and surfaced to the agent via MAF's `AgentSkillsProvider`. **HarnessAgent-only** — `ChatClientAgent` (bare chat) has no skills.

- **Plumbing** (`src/Aether.AI.Harness/Skills/`): `SkillRegistry` (name/description/category/content) + `ISkillRegistryContributor` + `ConfigureSkillRegistry`. Mirrors `ToolRegistry` but for static prompt data (no factory). `LoadFromDirectory(dir)` scans `<dir>/<skill-name>/SKILL.md` (frontmatter `name`/`description`/`category` + Markdown body).
- **Runtime source**: `AgentFactory.ConfigureSkillsProvider` builds an `AgentFileSkillsSource` (MAF) from `AetherAIOptions.SkillsDirectory` — discovers `SKILL.md` + scripts (`.py`/`.sh`/`.js` default) + resources, with a custom `AgentFileSkillScriptRunner` that runs scripts as subprocesses (`python3 <script> <args>`, returns stdout). Per-agent selection via `FilteringAgentSkillsSource` by `AgentDefinition.Skills` (empty = all).
- **Approval disabled by design**: the `AgentSkillsProvider` is built manually and injected via `HarnessAgentOptions.AIContextProviders` (the internal default provider is disabled) with `AgentSkillsProviderOptions.DisableLoadSkillApproval/DisableReadSkillResourceApproval/DisableRunSkillScriptApproval = true`. Chat has no approval UI; without this `run_skill_script` is blocked by MAF's default approval (which `DisableToolAutoApproval` does NOT cover).
- **Skills dir** (desktop): `AetherAIOptions.SkillsDirectory = <tenantDir>/skills`. Drop `<name>/SKILL.md` (+ optional `script.py`) and restart. `SkillRegistry` also scans it to feed the expert-edit skill picker (`ICustomAgentCatalog.GetAvailableSkills`).
- Agent opts in via `Skills` (name list; non-empty = enabled, empty = disabled — no separate toggle), persisted through the custom-agent pipeline (`AgentSourceFields.Skills`).
- `ToolStreamEvent` (tool call/result, paired by `CallId`) lives in `Aether.AI.Core.Agents` — constructed by `HarnessRuntime` from `FunctionCallContent`/`FunctionResultContent` in the stream. Keep it in Core (app/adapter contracts must depend on Core, not Harness internals).

### Agent 扩展能力（tools / MCP / skill / 长期记忆）

Agent 有三种扩展机制 + 跨会话长期记忆，全部在专家编辑器统一勾选/配置。选型：**业务层用 tools，外部用 MCP，流程知识用 skill，结构化参照知识（表 schema / 规则库，需跨流程复用）用 knowledge object**。Token 视角：tools/MCP 每轮带所有工具 schema（随工具数增长）；skill 每轮只带 name/desc 索引，正文 `load_skill` 时才进上下文（按需付费）；knowledge object 同样按需 `read` 才进上下文。

- **Tools**（进程内、强类型）：`ToolRegistry` + 各 `ai/<Context>/Acme.<Context>.AI` adapter 的 `AddXxxTools()` 注册 `AIFunction`，直接调 Application 契约。专家编辑器「内置工具」区按分类平铺勾选 + 权限 ComboBox（Safe/Confirm/Dangerous）。`ask_user` 自动纳入、隐藏在选择器。
- **MCP**（外部、跨进程/跨语言）：`Aether.AI.Mcp` 项目（alpha 包 `Microsoft.Agents.AI.Mcp` 隔离在此，opt-in）。
  - `McpServerRegistry`（`IMcpServerRegistry` in **`Aether.AI.Abstractions`** — the zero-ProjectReference contract package, NOT Hosting）：连接 stdio/HTTP server，预解析工具注册进 `ToolRegistry`（category `MCP`，默认 `Dangerous`，`RegisterMcpTool` TryAdd 防重）。相对命令（`dotnet`/`npx`）经登录 shell 跑（`zsh -lc '<cmd> <args>'`，POSIX 单引号转义）解决 GUI 受限 PATH；绝对路径直接跑。shared-task：`await StartAsync()` 等到连接真正完成（编辑器打开时 `EnsureLoadedAsync` 等它）。
  - 配置：运行时 `<tenantDir>/mcp-servers/*.json`（`McpServerConfigLoader` 兼容主流 `mcpServers` 映射 / 单对象 / 数组；`McpServerConfig.TryParse`/`ToJson` 用 mcpServers 格式，与 Trae/Claude Code/Cursor 互拷）。仓库根 `mcp/` 放自写 MCP server 源码（`mcp/SampleServer` 范例，不引用 Aether）。
  - 管理 UI：Experts 页「MCP工具」tab（`McpViewModel` + `McpView` + `McpServerEditWindow`）—— server 列表 + 连接状态 + 工具清单 + 增删改（单 JSON 文本框）+ 刷新。`IMcpManagementService`（**Abstractions** 接口，impl `McpManagementService` 在 Mcp 项目，写 `mcp-servers/<name>.json` + `RefreshAsync` 重连）。
  - 专家编辑器「MCP工具」区：按 server 分组卡片（名称+状态+错误），工具勾选 + 权限 ComboBox（和内置工具一致，覆盖进 `ToolApprovals`）。
- **Skill**（流程知识 + 轻量脚本）：见 [Skills](#skills-prompt--python-script-capabilities) 节。`run_skill_script` 的 `ParseCliArgs`（`AgentFactory`）兼容数组/对象/整串，并 `StripLeadingPrefix` 剥离 agent 可能带进来的 `python`/`<SQLQ>` 占位符/脚本路径（SKILL.md 的 Bash 写法 `python "<SQLQ>" ...` 与 run_skill_script 的"解释器+脚本已自带"模型不匹配，故剥离）。
- **长期记忆**（跨会话）：`AgentDefinition.EnableLongTermMemory` → `MemoryContextProvider`（Hosting，继承 MAF `AIContextProvider`）经 `ProvideAIContextAsync` 召回 `IMemoryStore` 记忆注入 `AIContext.Instructions`，`StoreAIContextAsync` 沉淀本轮 Q&A 为 `TaskHistory` 记忆项。区别于 `Memory`（会话内聊天历史窗口）。`IMemoryStore`（抽象）+ `SqliteMemoryStore`（`memory.db`）+ InMemory；注入靠 `AgentFactory` 的 `Func<AgentDefinition, AIContextProvider?>` 钩子（Harness 不直接引 Memory，保持解耦）。桌面单用户 → userId=null（全局记忆）。
- **专家编辑器统一 UI**（`ExpertEditView.axaml`）：每个配置块都是 Expander——「内置工具」（`ToolCategories`，按分类平铺 + 权限 ComboBox + 危险标）、「MCP工具」（`McpServerGroups`，按 server 分组卡片 + 权限）、「技能」（`Skills` 平铺勾选）。`GetAvailableTools` 过滤掉 MCP 工具（走 MCP 区）和 `ask_user`（自动纳入）。`ExpertsView.axaml.cs` 打开编辑器前 `await Mcp.EnsureLoadedAsync()` 确保 MCP 连完。

### Rule agent (无 LLM 的规则大脑)

A rule agent is a normal agent whose **brain is swapped from an LLM to deterministic rules** — it reuses the entire agent ecosystem (ToolRegistry / MCP / streaming / approval / ask_user / persistence / skill / long-term memory) and only changes「decide the next step」. The seam is `IChatClient`: `AgentDefinition.Engine == Rule` → `AgentFactory.Create` early-returns `BuildRuleAgent` → `new RuleChatClient(brain).AsHarnessAgent(options)`. Downstream is unchanged — it only reads `AIContent` out of `IChatClient` + `AIFunction` from `ToolRegistry`, doesn't care the brain is rules not an LLM.

- **Model** (`Aether.AI.Core.Agents`): `EngineKind { Llm, Rule }` (default `Llm`) on `AgentDefinition` (+ `Rules` = `RuleProgram` object — carried end-to-end, **never JSON** in the runtime path); `RuleProgram { Name, Steps[], NoMatchReply?, MaxSteps=20, Capture? }`, `RuleStep { Name?, Match, Action }`, `RuleMatch { OnUserRegex?, OnResultRegex?, MinToolCalls?, MaxToolCalls? }` (all-null = always), `RuleAction { Tool?, Args?, ReplyText? }` (`Tool` non-null → stream `FunctionCallContent`, loop continues; `ReplyText` non-null → stream `TextContent`, loop ends; mutually exclusive). `Args` is a `Dictionary<string,object?>` (structured, not a JSON string); `Capture` is a program-level regex whose capture groups feed `{user.N}` to **all** steps (so a step without its own `OnUserRegex` can still reference captured params — multi-step reuse without repeating the regex). The brain substitutes templates **per-value** on the dict (string leaves get `{user}`/`{user.N}`/`{result}` replaced, nested dict/list recurse, non-strings pass through) — paths/quotes/backslashes never break because there is no JSON to escape.
- **Engine** (`Aether.AI.Harness/Agents/`): `IRuleBrain`/`RuleContext` + `RuleProgramBrain` (stateless — each call derives context from `history`: latest user msg, latest `FunctionResultContent`, tool-call count this turn; first matching step's action fires; no match → `NoMatchReply`; `MaxSteps` hard-stop. Guaranteed convergence by design). `RuleChatClient : IChatClient` is the **agent-form** facade (MAF owns the loop). `BuildRuleAgent` reuses `BuildHarnessAgent` line-for-line but **turns off all injection-style providers** (`TodoProvider`/`AgentModeProvider`/skill-load/long-term-memory-recall) — rules can't consume injected NL context; the tool-execution surface (skill scripts, memory store) stays live. (Gotcha: MAF `HarnessAgent` defaults `TodoProvider` on, injecting a 2nd「### Current todo list」user msg that pollutes `BuildContext.LatestUser` — must `DisableTodoProvider=true`.)
- **Two facades, one brain** — rules have **two forms** sharing the same `RuleProgramBrain`:
  - **Agent form** (`RuleChatClient`): a standalone rule agent, summoned to chat like any agent — **zero LLM** the whole way. MAF framework owns the loop.
  - **Tool form** (`RuleToolExecutor` → `run_rule` `AIFunction`, cat「规则」, `Safe`): an LLM agent calls `run_rule(name, input)` once and gets a compact result; the executor runs the tool loop internally and the raw tool results are **hidden from the LLM**. Saves tokens three ways: no decision-reasoning tokens, no raw-result tokens, and business tools stay out of the LLM's tool schema (only `run_rule` is added). `RuleRegistry` dispatches by name; `RuleTool.Create` wraps it. Registered in `AddDesktopCommon` (`ConfigureToolRegistry`).
- **Persistence** — rule agents are a **5th note node type** `NoteNodeType.Rule = 4` (UI「规则」, icon `rule`, amber `#B45309`, `syntax=yaml`; see [Note node types](#note-node-types-5-种-form-节点)). `RuleSourceParser` (`IRuleSourceParser`, `business/Notes/Acme.Notes.Infrastructure/Agents/`, **separate from `AgentSourceParser`**): a **single YAML document** (no front-matter, no `engine` field — engine is hardcoded `"Rule"`). Metadata (name/description/category/tools/toolApprovals/memory/maxHistory/model/requireToolApproval) + program (steps/noMatchReply/maxSteps) coexist at the top level; the program part is serialized into `CustomAgentDefinition.SystemPrompt` and parsed back by `RuleProgramYaml`. Layering: Notes.Infrastructure can't reference Core's `RuleProgram`, so a small step DTO is duplicated (round-trip-identical). `CustomAgentCatalog` dispatches by NodeType: `Agent→IAgentSourceParser`, `Rule→IRuleSourceParser`; `ListAsync` lists both + registers each Rule def's program into `RuleRegistry` (idempotent overwrite) so the same program auto-powers both facades. `CustomAgentDefinition.Engine`/`RulesJson` + `CustomAgentRunner.ToAgentDefinition` map to `AgentDefinition.Engine`/`Rules`.
- **UI** — the Experts page has a **「规则」tab** (`RulesViewModel` + `RulesView`): rule agent cards (list/summon/edit/delete), filtered by `CustomAgentDefinition.NodeType == Rule`. Editing uses an independent `RuleEditViewModel` + `RuleEditView`/`RuleEditWindow` (上下两栏: 上=元数据表单, 下=规则程序 YAML 源码, 与笔记页两栏一致). Rule agents are summoned to chat like normal agents (`ChatTargetKind.Rule`, also routed through `ICustomAgentRunner`); rules have **no plan/execute mode** (`HasModeSupport` false). Cross-VM refresh: `NotesViewModel.NotesChanged` → `Rules.LoadAsync()` too.

### Note node types (5 种 form 节点)

笔记树承载 8 种节点（`NoteNodeType`，`business/Notes/Acme.Notes.Domain`）：`Note=0`（纯文本/markdown）+ 7 种 **form/代码节点**——`Agent=1` / `Workflow=2` / `Knowledge=3` / `Rule=4` / `CodeRule=5` / `CodeStrategy=6` / `Strategy=7`。共用 `note_node` 表，差异只在 `node_type` + `content` 编码。`NoteNodeTypeRegistry`（`apps/Acme.Shell`）集中登记每类的描述符——除显示元数据（UI label / icon / syntax / 新建模板 / 默认内容）外，还带 **3 个能力旗标**：`IsFormNode`（有右栏表单：Agent/Rule/CodeRule/Workflow/Knowledge；策略族/Note=false→全宽代码编辑器）、`HasAgentRunner`（源码直改后失效 `ICustomAgentRunner`：Agent/Rule/CodeRule/Workflow）、`IsChatTarget`（可召唤到聊天：Agent/Rule/CodeRule/Workflow）。新增类型在此加一行带旗标即可，避免散落 switch；未知类型回退 `Note`。两类家族：**agent 家族**（Agent/Rule/CodeRule/Workflow/Knowledge，有 edit-VM+catalog+parser）vs **strategy 家族**（Strategy/CodeStrategy，无 edit-VM/catalog/parser，走 `StrategyNoteSource`+`StrategyScriptingService` 独立限界上下文）。Form 节点的右栏表单 VM 由 **`INoteNodeEditVmFactory`**（`apps/Acme.Shell/NoteNodeEditVmFactory.cs`）注册表派发——每个 form 类型一个工厂（封装查同级 VM + 建编辑 VM + 接 Save/AutoSave/Cancel 事件，含 CodeRule 的 C# body 回填、Knowledge 的 body 重解析），`NotesView.CreateEditVmForNodeAsync` 经 `DesktopApp.Services` 定位器建字典查表（替代旧 130 行 if 链）。新增 form 类型 = 加描述符行 + 加一个工厂 + 注册。Form 节点在笔记页共用上下两栏布局（上=表单, 下=源码: `ExpertEditView`/`WorkflowEditView`/`KnowledgeEditView`/`RuleEditView`）；纯代码节点编辑器跨满。各 form 节点的持久化 parser 不同（Agent/Workflow/Knowledge 走 `AgentSourceParser`(YAML front-matter+body)/`WorkflowSourceParser`(JSON)/`KnowledgeSourceParser`(YAML front-matter+body)；Rule 走 `RuleSourceParser`(单 YAML 文档)——见 [Rule agent](#rule-agent-无-llm-的规则大脑)）。

### Knowledge objects (知识对象 / 微型知识图谱)

笔记树 4 种 form 节点之一（`NoteNodeType.Knowledge = 3`，UI 显示「知识对象」，强制 `syntax=yaml`、icon `knowledge`；见 [Note node types](#note-node-types-5-种-form-节点)）。**最简通用知识模型**：`KnowledgeObjectDefinition { Kind, Links[], Body }`（`business/Notes/Acme.Notes.Domain/Knowledge/KnowledgeObjectDefinition.cs`），`KnowledgeLink { Role, TargetId?, Target }`。持久化为 YAML front-matter（`kind` + `links`）+ markdown body（`KnowledgeSourceParser`，YamlDotNet，容忍无 front-matter 的老笔记），与 Agent 笔记同构；`name` = 笔记标题（不在内容里）。区别于 Agent（多字段）/ Workflow（JSON）/ Rule（单 YAML 文档）：知识对象只有 3 字段，**typed graph links 是它的定义性特征**——带 role 的图边指向其它笔记，`TargetId` 权威、标题回退（老数据无 id）。

- **AI 消费**（`KnowledgeTool` in `ai/Notes/Acme.Notes.AI/Tools/KnowledgeTool.cs`）：`ListKnowledgeObjects(parentId?)` 列所有/指定 folder 下 Knowledge 节点（body preview 80 字符）；`ReadKnowledgeObject(name)` → `FormatAsync` 拼装成一段 `Definition`：`kind:` / `name:` / body + `links:` 段，每个 link 输出 `[role] target:` + 目标笔记的**完整原始 Content**（含其自身 front-matter）逐行缩进 2 格。**只展开一层**——子节点自身的 link 不递归（不会无限套娃，也不回拉入口节点）。读是非破坏的、per-flow 的。`CreateKnowledgeObject(name,kind,body,linksJson?,parentId?)` 创建 KO 笔记（`Confirm` 级）；`UpdateKnowledgeObject(name,kind?,body?,linksJson?)` 部分更新（`Confirm` 级）——AI 现在能 CRUD 知识对象，闭环自迭代。
- **DAG 纪律（重要）**：边**单向**，只留「流程 uses/then → 资产」这类正向依赖边；**不要写反向回指边**（`consumed-by` / `schema-for` / `consumes` 等）——它们是冗余、且会被 `FormatAsync` 当噪音内联进 read 产物。分层：**流程层**（`kind=流程`）带 `uses`/`then` 出边，是消费/编排者；**资产层**（`kind=数据源`/`规则`，`links: []` 或只指向同级资产）是被引用的复用目标。
- **复用**：一个资产节点可被多个流程 `uses`。改一处 schema/规则，所有引用它的流程下次 `read` 都拿新版——这是单体 system prompt 做不到的。新场景 = 新建一个流程节点 + 勾选要复用的资产 + 可能加一两个专属规则，不用复制粘贴 prompt。
- **与 Agent 的混合（推荐）**：必须每次遵守的硬契约（输出格式、表范围约束等）留在 agent 节点的 body（system prompt）里确保可靠；重的参照数据（完整字段表、规则库、SQL 模板、示例输出）抽成知识对象按需 `read`。Agent body 里写一句「先用 KnowledgeTool 读『XX流程』」即可。
- **Gotchas**：
  - `NoteTool.CreateNote` 没有 nodeType 参数（只能建 `Note`），但 `KnowledgeTool.CreateKnowledgeObject` 专门建 Knowledge 节点（设 tags/syntax/content）。Knowledge 节点也可经 UI 新建或 `NoteService.CreateAsync(NodeType=...)` 直调。
  - link 靠标题解析时**标题必须唯一**；在 UI 里打开流程节点并保存一次，`KnowledgeEditViewModel.Build()` 会把标题解析成 `TargetId` 落库，之后改名/同名也按 id 精确命中。
  - `FormatAsync` 内联子笔记的 front-matter（含其 links），有轻微噪音但无害；清反向边后已最小化。

### Chat streaming surface (reasoning / approval / plan / mode / ask_user)

The chat page adapts to HarnessAgent's **full** streaming output. `RunStreamingCoreAsync` branches on every `AIContent` kind (see `StreamHandlers` above); `MainViewModelBase.RunSegmentedStreamAsync` renders each as a `ChatMessageItem` card. All thread through the **same** `RunSegmentedStreamAsync` cooperative loop, so agent + workflow paths both get them. Transcript is grouped into **`ChatTurnItem`**s (`Messages` is `ObservableCollection<ChatTurnItem>`, not flat) — each turn = user request + its agent items under a left-border container with status (Working/Done/Error/AwaitingApproval) + elapsed. Resume reconstructs turns by grouping on user-role messages.

- **Reasoning vs visible text**: `update.Text` concatenates **only `TextContent`** — `TextReasoningContent` (model's private "thinking") is structurally separate and reachable only via `update.Contents`. `NewTextSegment` sets `IsReasoning = isReasoningContent`: only `TextReasoningContent` segments are `IsReasoning=true` → 💭 card (streaming expanded, completed **collapsed** with elapsed, like Claude Code's "Thought for Xs"). `TextContent` segments (the model's **visible narration** between tools + the final answer) are `IsReasoning=false` → rendered as **expanded markdown** text (streaming = live `MarkdownContent` throttled ~6 tokens; frozen = markdown bubble). So only true thinking is collapsed; visible narration/answer are shown — not "everything collapsed". `FinalizeSegment` sets `IsStreaming=false` + `MarkdownContent=Content` on the last `TextContent`.
- **Tool approval — per-tool levels + per-expert override**: tools carry an `Aether.AI.Harness.Tools.ToolApprovalLevel` (declared by adapters at `ToolRegistry.Register`): `Safe` (read-only, auto-run), `Confirm` (reversible write, pop dialog), `Dangerous` (irreversible/order/delete/shell, pop dialog + red badge). When an agent's `RequireToolApproval` master toggle is on, `AgentFactory` wraps only **non-Safe** tools in `ApprovalRequiredAIFunction` (Safe auto-run). The expert author can **override per-tool** via `AgentDefinition.ToolApprovals` (`name→"Safe"/"Confirm"/"Dangerous"`, persisted as `tool_approvals` JSON in `AgentSourceParser`) — `AgentFactory.ResolveApprovalLevel` uses override > declared. The editor tool picker shows a level ComboBox per tool (default = declared) + red/amber badges. MAF approval is a **cooperative re-invocation loop, NOT a callback**: stream emits `ToolApprovalRequestContent` and ends the turn; host re-invokes `RunStreamingAsync` with a `ChatMessage` holding `request.CreateResponse(approved, reason)` (or `CreateAlwaysApproveToolResponse` for "don't ask again") on the **same** `frameworkSession`. `RunStreamingCoreAsync` stashes the original request (`ConditionalWeakTable<FrameworkAgentSession,…>` by `RequestId`); MAF's `ToolApprovalAgent` middleware (default-on) does binding/queuing/standing-rules. `ToolApprovalDecision` (Core DTO) carries the UI decision (`IApprovalDialogService` → `ApprovalDialogService` + `ApprovalWindow`). VM loop: run → if `OnApprovalRequest` fired, pop dialog → re-run with decision → resumed stream re-emits the approved tool's Call+Result, then the answer. `AutoApprovalRules` can auto-approve/defer but **cannot reject** — reject must go through the loop. If `RequireToolApproval` is off, ALL tools auto-run (levels inert).
- **`ask_user` interactive dialog tool**: a host-registered tool (`AddDesktopCommon`, `AskUserTool.AskAsync(AskUserQuestionInput[] questions)` → `IAskUserDialogService` + `AskUserWindow`: a **multi-question form** — each question a section with option buttons + custom text, one 提交 returns all answers as a JSON array in order; user 取消 returns `[]`). `AskUserQuestionInput{Question,Options}` lives in Acme.Shell (UI-agnostic). `AgentFactory` **auto-includes** `ask_user` in every agent (no per-agent Tools opt-in) and **auto-injects** a system-prompt instruction to use it for confirmations + batch multiple questions in one call (else the agent asks in plain text). It is **hidden from the expert tool picker** (`GetAvailableTools` filters it) — it's always-on infra. Registered as `Safe` → never gated by approval (it IS the interaction UI). Mirrors Claude Code's `AskUserQuestion` (which also takes 1–4 questions per call).
- **Plan UI (📋, reuse `TodoProvider`)**: `EnableTodoProvider` wires MAF's `TodoProvider` (`todos_add`/`todos_complete`/`todos_remove`/`todos_get_*`; items `{Id:int, Title, Description, IsComplete:bool}` — binary, no `in_progress`). After any `todos_*` result, the runtime resolves `agent.GetService<TodoProvider>()` + `GetAllTodosAsync(frameworkSession, ct)` and surfaces the live list via `OnTodoList`. VM renders/updates a 📋 plan card **in the transcript** (pinned to turn top, items[1]); completed items `TextDecorations="Strikethrough"`. `todos_*` calls are **suppressed from the generic tool-card path** (OnToolEvent skips `todos_*`). The plan card is **persisted** (`ToTranscriptMessage`: `kind="plan"` + `todos` JSON; `FromTranscriptMessage` rebuilds) — survives restart. Approval (`ItemType="approval"`) cards are runtime-only (skipped in `PersistTurnAsync`); `ApprovalState` (0/1/2) drives ⏳/✅/❌.
- **AgentMode plan/execute**: `EnableAgentModeProvider` wires MAF's `AgentModeProvider` (default modes `plan`=interactive / `execute`=autonomous; default mode `plan`). Mode is per-session state (`AgentSessionStateBag`). `HarnessRuntime.GetModeAsync/SetModeAsync` (resolve `agent.GetService<AgentModeProvider>()` + framework session); `RunStreamingAsync` takes a `desiredMode` param applied at run start (covers new-session-before-first-run). `ICustomAgentRunner`/`ICustomWorkflowRunner` thread `GetMode/SetMode` + `desiredMode`. Input area has a **plan/execute selector** (`HasModeSupport` = selected agent's `EnableAgentModeProvider`; set in `OnSelectedAgentItemChanged` **before** the `_isInitializing` guard or it won't show on startup). After each turn `RefreshModeAsync` re-reads the actual mode (catches agent self-`set_mode`). A **plan-accept bar** shows only when `HasModeSupport && SelectedMode=="plan" && !IsAgentRunning && lastTurnHasPlanCard` (signal-triggered, not every plan turn); `AcceptPlanCommand` → `SetModeAsync("execute")` + re-run a continuation turn.
- **Tool result rendering by type**: `ChatMessageItem.NormalizeToolResult` normalizes `Output` → `ResultKind` (text/code/table/error/json) + `ResultText` + `IsResultLong`; the tool card expanded section picks a template (text one-line, code monospace+scroll, error red, table/json fallback). Collapsed one-liner = `VerbIcon` (by tool-name keyword) + `ToolName(MainArg)`.
- Core DTOs (`ToolApprovalRequest`/`ToolApprovalDecision`/`TodoItemInfo`/`StreamHandlers`/`ToolApprovalLevel`) live in `Aether.AI.Core.Agents` or `Aether.AI.Harness.Tools` — MEAI types (`ToolApprovalRequestContent` etc.) stay confined to Harness. `TodoItem.Id` is `int` (not string).

## Non-obvious gotchas

- **共享 SQLite 基类 `src/Acme.Persistence`**：所有 SQLite-backed store（12 个 business Infrastructure repo + 平台 `SqliteConversationStore`/`SqliteMemoryStore`）继承 `SqliteStoreBase`，不再各自 copy-paste 连接串校验/`ForFile`/`OpenAsync`+busy_timeout/WAL/幂等 lazy schema init/`ExtractDataSourcePath`。基类 API：`static BuildConnectionString(dbPath)`（swap 缝）、`protected OpenAsync(ct)`/同步 `Open()`（busy_timeout=5000 + 可选 `ForeignKeysEnabled`）、`EnsureSchemaAsync(createSql, ct)`/同步 `EnsureSchema(createSql)`（`Interlocked` 守卫 + 建目录 + WAL + createSql + `MigrateAsync`/`Migrate` hook）、`protected static ExtractDataSourcePath(cs)`。`SqliteMigrations.AddColumn(Async)(conn, table, column, def)` 收拢幂等 ALTER（Notes `icon`/Ctp `auto_login`/Automation 3 列）。**全 async ConfigureAwait(false)**（库最佳实践 + `SqliteLlmConfigRepository` UI 线程 sync-over-async 依赖它不死锁）。新增 SQLite store = `: SqliteStoreBase, IXxx` + ctor `: base(cs)` + `ForFile => new(BuildConnectionString(p))` + `await EnsureSchemaAsync(CreateSql, ct)` + `await OpenAsync(ct)`，迁移进 `MigrateAsync` override。**`Microsoft.Data.Sqlite` 直引只在 `Acme.Persistence.csproj`**——consumer csproj 引 `Acme.Persistence` 即传递获得，删直引。Automation 用同步 `EnsureSchema(CreateSql)`（ctor，#3a）；Qifu 表重建迁移留 `MigrateAsync` override 内联（`PRAGMA table_info` 查 user_id→建新表→复制→换名）。各 repo 的 raw SQL 方言（`INSERT OR REPLACE` 等）仍是 SQLite 方言——swap-aware 非 swap-ready，真换库仍需逐个改 SQL。**不做 EF Core**（CRUD 代码库过度投入）。

- **CancellationToken 基线 + sync-over-async 卫生**：异步服务接口加 `CancellationToken ct = default` 末参是**默认参、源兼容**（既有调用方不改仍编译），但接口方法加参后所有**实现类**签名必须同步加（interface impl 必须匹配）。CT 只转发到**可取消的 I/O**（`IAppServerHttpClient` 5 方法、HTTP `HttpClient.GetXAsync(url, ct)`、`Task.Delay(ms, ct)`、已有 CT 的 repo）；**本地 SQLite 读不转发**（取消无意义，sub-ms）——`AnalysisManager` 里 `_securityLookup`/`_indicatorCalculator`/`_quoteRepository`、`SecurityClientSyncService` 里 `_securityRepository.AddRangeAsync` 都不转发 ct（注释说明）。MEAI `AIFunctionFactory.Create(method, tool)` 自动绑定运行时 CT（不暴露为 JSON schema 参），故 AI 工具方法加 `CancellationToken cancellationToken = default` 末参即被 agent 运行时取消。**sync-over-async 死锁规则**：UI 线程（`OnFrameworkInitializationCompleted`→`ConfigureServices`→`AddDesktopCommon`）上 `.GetAwaiter().GetResult()`/`.Wait()` 仅在被调 async 已 `ConfigureAwait(false)`、或用 `Task.Run(...)` 包裹（丢 SynchronizationContext）、或被调方同步完成（`Task.FromResult`）时安全。`SqliteLlmConfigRepository` 因被 `DesktopLlmBootstrap` UI 线程 sync-over-async 消费故全方法 `ConfigureAwait(false)`；`SqliteAutomationTaskRepository` ctor 一次性 schema 初始化改用同步 SQLite API（`conn.Open()`/`cmd.ExecuteNonQuery()`）避免 ctor 里 async-over-sync。`JsonPreferencesStore.GetAsync` 是 `Task.FromResult`（同步完成无 I/O）→ 构造期/VM 读 `.GetAwaiter().GetResult()` 安全；`SetAsync` 真异步，UI 线程调必须 `Task.Run(...).Wait()`。
- **ABP auth `scope`**: login MUST send `scope = "Abp alphaagent_chat"` (set in `AddDesktopCommon`). Without it, the token lacks the `Abp` API audience → `401 Bearer error="invalid_token"` on all protected endpoints. Refresh does NOT need scope (refresh token preserves scopes).
- **`TenantHeaderDelegatingHandler`**: registered on `IAppServerHttpClient` ahead of `BearerTokenDelegatingHandler`. Sends `__tenant` header (tenant name from `AppServerOptions.Tenant`). `AppServerOptions` is a **plain singleton** (not `IOptions`), so inject it directly — `IOptions<AppServerOptions>` returns a default empty instance.
- **`APP_BASEURL` 配置**：`AppServerOptions.BaseUrl` 优先级：env `APP_BASEURL` → preferences `app.serverUrl`（从 `<tenantDir>/preferences.json` 读）→ 空。登录窗口有"服务器地址"输入框，登录前 `IAppAuthService.ConfigureBaseUrl(url)` 设置 `HttpClient.BaseAddress` + `AppServerOptions.BaseUrl`，并持久化到 preferences。`DesktopCompositionExtensions` 启动时直接读 preferences JSON 文件（DI 未构建，不能注 IPreferencesStore）。
- **`IAppServerHttpClient.PostAsync<T>` has `where T : class`** — can't use `Guid?`/`bool`. Use `PostRawAsync` + manual parse for value-type responses.
- **`AgentSourceParser.Serialize`** takes a `CustomAgentDefinition` directly (not positional params, not an `AgentSourceFields` type — that no longer exists). Add a new persisted agent field by: extending `CustomAgentDefinition` (Notes Domain) + a parse case in `ParseFrontMatter` (keys are lowercased + underscore-stripped) + the `Serialize` output line + `CustomAgentRunner.ToAgentDefinition` (→ platform `AgentDefinition`) + `AgentDefinition` itself + `ExpertsViewModel` (2 mappings) + `ExpertItem`/`ExpertEditViewModel`/`ExpertEditView.axaml`. List values reuse `ParseListValue` (flow `[a,b]` or block `- a`); maps persist as JSON single-line (see `tool_approvals`). `RequireToolApproval` + `ToolApprovals` (2026-08) are the worked example.
