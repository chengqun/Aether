## Build, test, run

Single solution: `Aether.AI.Platform.slnx` (note: `.slnx`, not `.sln`). .NET 10.

```bash
# git submodules — init before first build (shallow, pinned to a fixed commit)
git submodule update --init externals/Lean externals/FlaUI-MCP   # Lean = futures engine; FlaUI-MCP = Windows desktop-control MCP server (optional, Windows-only)

dotnet build Aether.AI.Platform.slnx          # build everything
dotnet test  Aether.AI.Platform.slnx          # run all test projects

# Single project build/test (dotnet build/test accept ONLY ONE project in this env)
dotnet test tests/Aether.AI.Harness.Tests/Aether.AI.Harness.Tests.csproj --filter "FullyQualifiedName~Memory"

# Run the desktop app (Avalonia; Stockapp tenant with CTP/Quotes/Trading; Qifu tenant with Yushu/CloudDocs)
dotnet run --project apps/Stockapp/Acme.Stockapp.Desktop
dotnet run --project apps/Qifu/Acme.Qifu.Desktop

# Run the ABP server backend (server/; migrated from AlphaAgent.Web)
#   HttpApi.Host = API + OpenIddict OAuth2 + SignalR (:44319) — Aether desktop/mobile clients talk to this
#   Blazor       = admin panel (:44337)
# Directly runnable locally: appsettings.Development.json (gitignored, real dev values) overrides the
# ${...} placeholders in appsettings.json, and openiddict.pfx (committed dev cert) is embedded. CI deploy
# to IIS via .github/workflows/deploy-iis.yml injects production secrets into appsettings.json at publish.
dotnet run --project server/Aether.Server.HttpApi.Host
dotnet run --project server/Aether.Server.Blazor
```

The first build after init is slow (Lean source compiles). Lean's transitive deps emit NU1902/3/4 vulnerability advisories (System.Drawing.Common / WCF / WinHttpHandler) — advisory only, expected.

## Big-picture architecture

A multi-context DDD platform built on **Microsoft Agent Framework** (`Microsoft.Agents.AI`, wrapped by `src/Aether.AI.Harness`). Top-level layout enforces a strict layering:

- `src/` — the **Aether.AI platform** itself, standalone. `Aether.AI.Abstractions` (zero-ProjectReference contract package — MCP contract types `McpServerConfig`/`IMcpServerRegistry`/`McpServerEntry`/`McpToolInfo`/`McpServerStatus`/`IMcpManagementService`; one stable PackageReference `Microsoft.Extensions.AI.Abstractions` for `AIFunction`; the **only** `Aether.AI.*` project `business/` may reference — `Acme.AppAutomation.McpClient` consumes `IMcpServerRegistry`/`McpServerConfig` from here), `Aether.AI.Core` (framework-agnostic domain, zero deps — incl. `Conversations.Runs` event-stream model: `AgentRun`/`AgentEvent`/`AgentEventPayload`), `Aether.AI.Harness` (AgentFactory/HarnessRuntime/SessionManager/ToolRegistry/SkillRegistry/IChatClientFactory wrapping MEAI; `EventHistoryRebuilder.RebuildLlmHistory` rebuilds LLM history from the typed event stream on cross-restart restore), `Aether.AI.Workflows` (WorkflowFactory wrapping MAF Workflows — peer of Harness, does NOT depend on Harness), `Aether.AI.Memory` (`IConversationStore` abstraction + InMemory impl; event-stream API: `AppendRunAsync`/`GetRunsAsync`/`GetEventsAsync`), `Aether.AI.Memory.Sqlite` (SQLite impl, opt-in — `conversation`/`agent_run`/`agent_event` three tables), `Aether.AI.Hosting` (`services.AddAetherAI()` DI entry point + DefaultChatClientFactory + ConversationTitleService). Platform source never references `business/` or `ai/`.
- `business/` — **pure DDD bounded contexts**, each `Acme.<Context>.{Domain,Application,Infrastructure}`. AI-free.
- `ai/` — **business AI adapters** bridging Aether and each context. Peers of `business/`, kept separate so business stays AI-free. 9 tool adapters (`Ctp/Quotes/Qifu/Notes/Trading/ApkParser/SystemTools/DataQuery/StockTrading`) + 1 agent bridge (`Agents`). Not every context has an AI adapter — e.g. Automation has none (its business port `IAgentExecutor` is implemented host-side; see [business-port pattern](#business-domain-port--host-implementation) below). The **agent bridge** `ai/Agents/Acme.Agents.AI` is NOT a tool adapter — it registers `ICustomAgentCatalog`/`ICustomAgentRunner` (CRUD + run-time for custom agents), not tools. It is the only adapter that doesn't follow the "register tools only" convention, by design.
- `externals/` — third-party engines: `Ctp.Net.Core` (native CTP wrapper), `Lean` (QuantConnect Lean, git submodule), and `FlaUI-MCP` (Windows desktop-control MCP server, git submodule; consumed by the [AppAutomation](#appautomation-context-桌面控制--固定过程) MCP path).
- `apps/` — consumers/hosts: `Acme.Desktop.Mvvm` (UI-agnostic shell VM library), `Desktop/Acme.Desktop.Shared` (Avalonia views + composition root), `Desktop/Acme.Desktop.Workbench` (data-driven shell engine + JSON theme system + `WorkbenchWindow`), `Qifu/Acme.Qifu.Desktop` + `Stockapp/Acme.Stockapp.Desktop` (tenant host apps). (Qifu 不在 slnx 注册——Stockapp 同步 GitHub 时 Qifu 隐藏.) See [Desktop architecture](#desktop-architecture) + [Workbench shell + theme system](#workbench-shell--theme-system).
- `server/` — the **ABP backend server** (`Aether.Server.*`, migrated from the standalone `AlphaAgent.Web`). Not part of the DDD/AI layering — a self-contained ABP 10.4.1 tiered app that the desktop/mobile clients authenticate against (OAuth2 `alphaagent_chat` + `api/app/*` REST + SignalR `/hubs/chat`). 10 ABP-layered sub-projects + 2 runnable hosts. See [Server context (ABP backend)](#server-context-abp-backend) below.
- `tests/` — all test projects live here, never interleaved with source.

### DDD layering rules (enforced; verify before changing csprojs)

- **Domain** = pure: zero `ProjectReference`, no SDK/HTTP/SQLite/logging packages, no `Aether.AI.*`. Entities/value-objects/ports only. A Domain may reference another context's Domain (shared kernel) — e.g. 8 contexts reference `Acme.AppAuth.Domain`.
- **Application** → Domain (+ foreign Domain port). Never Infrastructure/AI/externals.
- **Infrastructure** → Domain (+ externals + foreign Domain contract). Never another context's Infrastructure.
- **`business/` must NEVER reference `Aether.AI.*`.**
- Dependency graph is a DAG; no cycles. `Acme.AppAuth.Domain` is the pure source (foundation), `Acme.Trading.Runtime.Lean` the pure sink.

### AI adapter convention (`ai/<Context>/Acme.<Context>.AI`)

Every **tool adapter** is the same shape (mirror `ai/Ctp`):
- csproj: `Aether.AI.Hosting` + the context's **Application** project (never Infrastructure/Domain directly).
- `AddXxxTools(this AetherAIBuilder)` registers tools ONLY — there is **no** `AddXxx(modelId)` agent method. Agents are built dynamically by the host/page from the shared tool pool. `ToolNames[]` + `CreateTool<T>` helper using `AIFunctionFactory.Create`.
- Tool classes live in `Tools/`, namespace `Acme.<Context>.AI.Tools`. Tools call Application contracts, never Domain/Infrastructure.
- `AddXxxTools` registers TOOLS ONLY — the host composition root wires business layers.
- **例外：`ai/Quotes/Acme.Quotes.AI`** 是跨上下文工具适配器——引 `Securities.Application`（`SecurityQueryTool` 用 `ISecurityService` 查证券）+ 在 `AddQuotesTools` 注册 `ISecurityLookup` ACL 适配器（`SecurityLookupAdapter` 桥接 `ISecurityManager`→`ISecurityLookup`，让 Quotes 不直接依赖 Securities）。因 Quotes 工具需 Securities 数据，ACL 桥接是设计决策。`ai/Trading/Acme.Trading.AI` 引 `Trading.Scripting`（`CreateStrategyTool` 用 `StrategyScriptCompiler` 即时编译验证）+ `Notes.Application`（策略笔记持久化）+ `Trading.Runtime.Domain`（运行时端口/枚举）——同理例外。

The **bridge adapter** `ai/Agents/Acme.Agents.AI` is a different shape:
- References `Aether.AI.Hosting` + `Aether.AI.Workflows` (runs custom workflows via `WorkflowFactory`) + `Acme.Notes.Application` (custom agents persisted as Notes) + `Acme.AppAuth.Application` (for `IAppServerHttpClient`, marketplace client).
- `AddCustomAgents(this AetherAIBuilder)` registers `ICustomAgentCatalog` (CRUD over Notes-backed agents via `AgentSourceParser`), `ICustomAgentRunner` (maps `CustomAgentDefinition` → `AgentDefinition` → `HarnessRuntime`), `IAgentMarketplaceService` (cloud agent catalog client).
- `AddCustomWorkflows(this AetherAIBuilder)` registers `ICustomWorkflowCatalog` (CRUD over Notes-backed workflows via `WorkflowSourceParser` — JSON, not YAML) + `ICustomWorkflowRunner` (builds participants via `AgentFactory`, wraps as MAF Handoff workflow via `WorkflowFactory.BuildAsAIAgent`, runs through `HarnessRuntime.RunStreamingAsync(AIAgent,…)` — reuses the same `RunStreamingCoreAsync` extraction loop as agents). Workflow persistence: `WorkflowSourceParser` (JSON content, `NoteNodeType.Workflow`) in `business/Notes/Acme.Notes.Infrastructure/Agents/`. Fields: name/description/category/entry_agent_id/participants/handoffs/handoff_instructions.
- Custom agent persistence: `AgentSourceParser` (YAML front-matter + Markdown prompt) in `business/Notes/Acme.Notes.Infrastructure/Agents/`. Fields: name/description/category/tools/skills/memory/max_history/model/top_p/max_output_tokens/response_format/enable_web_search/enable_todo_provider/enable_agent_mode_provider/enable_file_memory/enable_agent_skills/enable_open_telemetry/source/marketplace_id/marketplace_synced_at/display_name. `Serialize(CustomAgentDefinition)` takes the definition directly. Business layer defines its own `AgentMemoryMode`/`AgentResponseFormat` enums (parallel to Core's) — adapter maps them, so `Aether.AI.*` never leaks into Notes.

### Business Domain port → host implementation

When **business logic must trigger agent execution** (or anything AI/platform-specific) but business cannot reference `Aether.AI.*`, define a **port interface in the context's Domain** and implement it **in the host composition root**. This is the canonical pattern — do NOT create an `ai/` adapter just to host a port impl, and do NOT make business depend on AI.

- **Port** in `Acme.<Context>.Domain.Interfaces` (e.g. `IAgentExecutor`). Domain stays pure; the Infrastructure service/scheduler depends on the port, not on AI types.
- **Implementation** lives in an AI-aware host project (`apps/Acme.Desktop.Mvvm` or `apps/Desktop/...`), depending on platform/AI types (`ICustomAgentRunner`, `IConversationStore`, …), NEVER on business Infrastructure.
- **Registration** at the composition root (`AddDesktopCommon`): `services.AddSingleton<IPort, HostImpl>()`.
- **Reuse, don't re-route**: the impl should call the *same* runtime path the UI uses, not a parallel one. Canonical example — `ConversationBackedAgentExecutor` (`apps/Acme.Desktop.Mvvm`): Automation's scheduler calls `IAgentExecutor.ExecuteAsync`; the impl runs the agent via `ICustomAgentRunner.RunStreamingAsync` and persists the turn to `IConversationStore` (one `AgentRun` + a single `TextChunk` `AgentEvent`), so scheduled runs land in「最近会话」with cross-fire memory — identical to the chat page's flow. Each task owns a stable `ConversationId` (stored on the entity) so fires thread into one conversation.
- The business layer raises completion via a port event (`IAutomationScheduler.TaskCompleted`); the host VM subscribes and refreshes UI (task list + recent conversations) on the dispatcher thread.

Reference: Automation is the working template — `business/Automation/` (Domain port + scheduler) + `apps/Desktop/Acme.Desktop.Mvvm/ConversationBackedAgentExecutor.cs` (host impl) + `AddDesktopCommon` (registration).

### Foundation context

`business/AppAuth/` (`Acme.AppAuth.*`, DI classes named `Platform*Extensions`) is the **foundation**: app-server (ABP) OAuth2 auth + authenticated HTTP (`IAppServerHttpClient` with `TenantHeaderDelegatingHandler` + `BearerTokenDelegatingHandler`) + `ICurrentUser`. Other contexts consume its ports — never the reverse.

### Server context (ABP backend)

`server/` (`Aether.Server.*`, migrated from the standalone `AlphaAgent.Web`) is the **ABP backend** the desktop/mobile clients authenticate against. It is a self-contained ABP 10.4.1 tiered app — **not** part of the DDD/AI layering (`src/`+`business/`+`ai/`). All `ProjectReference`s are internal (no dependency on Aether platform/business); `business/AppAuth` is its client-side peer (talks to it over HTTP, never references it). .NET 10 + SQL Server (`Volo.Abp.EntityFrameworkCore.SqlServer`) + OpenIddict OAuth2 + SignalR + Serilog + Autofac. Redis only in DbMigrator.

**10 ABP-layered sub-projects** (standard ABP tiered template, all renamed `AlphaAgent.Abp.*`→`Aether.Server.*`): `Domain.Shared` / `Domain` / `Application.Contracts` / `Application` / `EntityFrameworkCore` / `HttpApi` / `HttpApi.Client` / `HttpApi.Host` / `Blazor` / `DbMigrator`. `common.props` at `server/common.props` (sub-projects reference `..\common.props`). **ABP module classes stay `Abp*Module`** (e.g. `AbpHttpApiHostModule`/`AbpBlazorModule`/`AbpDomainModule`) — they never contained "AlphaAgent", so the namespace rename left `[DependsOn(typeof(AbpXxxModule))]` zero-change. This is why the migration was low-risk despite ~315 source files.

**2 runnable hosts** (+1 console tool):
- **`HttpApi.Host`** (`:44319`) — the API server Aether clients talk to. Serves OpenIddict OAuth2 (`/.well-known`, `/connect/token`) + `api/app/*` REST + Swagger + SignalR `/hubs/chat`. Host module `AbpHttpApiHostModule` maps `ChatHub` at `/hubs/chat` and creates conventional controllers from `AbpApplicationModule.Assembly` → ABP default route `api/app/<service-slug>` (no custom route template). Also hosts `DailySyncBackgroundService` (runs daily 20:01 local — syncs futures data + stock-picking strategies that publish Moments/service-account articles).
- **`Blazor`** (`:44337`) — admin panel (LeptonXLite 5.4.1 theme; 5.4.1 vs ABP 10.4.1 mismatch is known but runs — version upgrade is an optional follow-up). 7 custom admin pages under `Components/Pages/`: `AgentConfigManagement` / `AgentUsage` / `LlmConfigManagement` / `Moments` / `SecurityManagement` / `ServiceAccountManagement` / `VersionConfigManagement` (+ stock ABP admin UI).
- **`DbMigrator`** — console EF Core migration/seeding tool. 28 migrations in `EntityFrameworkCore/Migrations/` (table prefix `App`, migration history preserved → DB-compatible).

**Custom domain** (`Aether.Server.Domain`, 16 `App*` entities): `AppConversation`/`AppConversationParticipant`/`AppChatMessage` (chat + social messaging), `AppMoment`/`AppGroup`/`AppRelationship` (社交/moments/contacts), `AppDevice` (device registry), `AppSecurity` (securities catalog, ~5400 rows incl. ~250 futures — synced by `SecurityAppService`/`DailySyncBackgroundService`, consumed by Quotes client-side sync), `AppNoteNode` (cloud-synced notes), `AppLlmConfig` (cloud LLM configs), `AppServiceAccount`/`AppServiceAccountPost` (服务号), `AppVersionConfig` (app version distribution), `AppAgentUsageRecord` (agent usage telemetry), `AppYushuToken`/`AppCloudDocsToken` (Qifu tenant SSO tokens). **13 app services** (`Aether.Server.Application`) expose these as `api/app/<slug>`: `Chat`/`Moment`/`Group`/`Device`/`Security`/`NoteNode`/`LlmConfig`/`ServiceAccount`/`VersionConfig`/`AgentUsage`/`AgentMarketplace`/`YushuToken`/`CloudDocsToken`.

**ChatHub** (`HttpApi/Hubs/ChatHub.cs`, raw SignalR `Hub` not `AbpHub`, route `/hubs/chat`): dual-auth (JWT `sub` claim for users, or `authorizationCode` query param for devices). Methods: `SendMessage(conversationId, content, type)` (broadcasts to `conv_{id}` group via `IChatNotifier`, fires unread-count + new-conversation notifications) / `MarkAsRead` / `JoinConversation` (on connect, auto-joins all the user's conversation groups). This is the real-time backbone for the MAUI mobile social feed + desktop chat.

**OpenIddict** (`Domain/OpenIddict/OpenIddictDataSeedContributor.cs`, host-only seed): scopes `Abp` + `alphaagent_chat`; 3 clients — `Abp_BlazorServerTiered` (Confidential, Hybrid), `Abp_Swagger` (Public, AuthorizationCode), **`Aether_Chat`** (Confidential, **Password + RefreshToken** grants — this is the Aether desktop/mobile client's grant). The `Aether_Chat` client's `ClientId` VALUE is `"alphaagent_chat"` (preserved on migration for client-contract compat) — note the config *key* `Aether_Chat` ≠ the *value* `alphaagent_chat`. ClientSecret read from `OpenIddict:Applications` config; code fallback `"chat_secret"`. **Client-side scope must be `"Abp alphaagent_chat"`** (both scopes) or the token lacks the `Abp` audience → `401` on protected endpoints — see [ABP auth scope gotcha](#non-obvious-gotchas).

**Naming preserved on migration (compat)**: OpenIddict clientId **value** `alphaagent_chat` + DB name `AlphaAgent` (connection string `Database=AlphaAgent`) + `Abp*Module` class names + table prefix `App` + migration history. Changing namespace/ProjectReference paths was the only rename.

**Config / secrets split (directly runnable locally, GitHub-safe)** — mirrors the original AlphaAgent.Web design:
- `appsettings.json` (git-tracked) = **template** with `${...}` placeholders (`${CONNECTION_STRING}`/`${PASSPHRASE}`/`${CERT_PASSWORD}`/`${CLIENT_SECRET}`/`${VERSION_PUBLISH_TOKEN}`). **No secrets.** .NET does NOT expand `${...}` — these are literal until replaced.
- `appsettings.Development.json` (gitignored — `appsettings.Development.json` is a global ignore) = **real local dev values** (SQL Server `117.72.186.128,1433` + sa password + passphrase + cert password + `chat_secret` + `dev-token`). Loaded only in `Development` env → **overrides** the placeholders → server runs directly. Real dev creds never enter git.
- `openiddict.pfx` (git-tracked, in `HttpApi.Host` + `Blazor`) = self-signed **DEV** signing cert (ABP template convention; committed in the original AlphaAgent repo too). csproj embeds it as `EmbeddedResource` via `<ItemGroup Condition="Exists('./openiddict.pfx')">` — absent → build still passes (Condition skips) but OpenIddict can't sign tokens at runtime → startup fails. The real secret is the cert **password** (`b677a31c-...`, in gitignored dev settings), not the cert itself.

**Running locally (directly runnable — dev values + pfx are in place)**: `dotnet run --project server/Aether.Server.HttpApi.Host` (ASPNETCORE_ENVIRONMENT=Development → dev settings override) → Swagger `https://localhost:44319/swagger`. First run on a fresh DB: `dotnet run --project server/Aether.Server.DbMigrator` (creates schema + seeds OpenIddict clients + admin user). The `AlphaAgent` DB at `117.72.186.128` already exists + is seeded, so DbMigrator is only needed for a new DB.

**CI deploy to IIS** (`.github/workflows/deploy-iis.yml`, migrated from AlphaAgent): on push to `main` touching `server/**` — `dotnet publish server/Aether.Server.HttpApi.Host -c Release --self-contained true --runtime win-x64` → PowerShell replaces the `${...}` placeholders in `./publish/appsettings.json` with GitHub Secrets (`CONNECTION_STRING_DEFAULT`/`STRING_ENCRYPTION_PASSPHRASE`/`OPENID_DICT_CLIENT_SECRET`/`VERSION_PUBLISH_TOKEN`/`OPENID_DICT_CERT_PASSWORD`) → msdeploy to IIS (Web Deploy `:8172/msdeploy.axd`, secrets `IIS_SITE_NAME`/`IIS_SERVER_HOST`/`IIS_USERNAME`/`IIS_PASSWORD`). Fresh CI checkout has no `appsettings.Development.json` (gitignored) so only the placeholder `appsettings.json` ships, then gets secret-injected — production secrets never touch git. Only HttpApi.Host is CI-deployed (Blazor admin panel is not — matches original). Required GitHub Secrets: the 5 config-replacement + 4 IIS msdeploy ones listed above.

### Trading + Lean (the engine-bridge pattern)

The 回测/实盘 page, the business Trading context, and the Lean runtime are **four separated layers** with a one-way dependency. The UI and business layers never reference Lean — swapping the runtime is a DI-only change.

```
Desktop 回测/实盘页  (TradingViewModel + TradingView, apps/Stockapp)   ← runtime-agnostic
        ↓ depends on
Trading.Application  (IBacktestApplicationService / ILiveTradingApplicationService)   ← orchestration, Lean-neutral
        ↓ depends on
Trading.Runtime.Domain  (ports: IBacktestRuntime / ILiveTradingRuntime; BarResolution; LiveTradingRuntimeStatus; MarketDataConnectInput)
        ↑ implemented by
Trading.Runtime.Lean  (LeanBacktestRunner / LeanLiveTradingService / CtpBrokerage / TradingHostAlgorithm)   ← the ONLY project referencing externals/Lean
        ↓ consumes (DI-provided, not self-registered): ICtpSession (Ctp context) + IAnalysisManager (Quotes context)

Trading.Domain  (IStrategy / MarketBar / SignalDirection / BacktestResult / BacktestStatistics / EquityPoint / StrategyRegistry)   ← pure, shared by Application + Lean
```

- **`business/Trading/Acme.Trading.Domain`** — pure: `IStrategy` (`WarmUpBars`/`Initialize`/`EvaluateSignal→SignalDirection` + `ParameterDefinitions` 接口默认返回空，策略可选覆盖声明参数供 UI 动态渲染), `StrategyParameterDef` (`Key`/`Label`/`DefaultValue`), `MarketBar`, `BacktestResult` (`Statistics`/`EquityCurve`/`Logs`), `StrategyRegistry` (static; `Register`/`Unregister`/`Create`/`GetRegisteredNames()`/`GetParameterDefinitions(name)` feeds the UI strategy picker + 参数 UI). 内置策略已删——全部走动态加载。
- **`business/Trading/Acme.Trading.Application`** — `IBacktestApplicationService.RunAsync(BacktestRunInput)→BacktestResult` and `ILiveTradingApplicationService` (`StartAsync(LiveTradingRunInput)→(bool,string?)`, `StopAsync`, `Status`/`IsRunning`, `StatusChanged`/`LogReceived` events). Thin mappers to the runtime ports. `AddTradingApplication()` registers both.
- **`business/Trading.Runtime/Acme.Trading.Runtime.Domain`** — the runtime **ports** (`IBacktestRuntime`, `ILiveTradingRuntime`) + shared enums/DTOs. No Lean.
- **`business/Trading.Runtime/Acme.Trading.Runtime.Lean`** — the **only** project referencing `externals/Lean`. `LeanBacktestRunner` (full backtest: reads K-line via `IAnalysisManager` → CSV → LEAN engine → `BacktestResult`). `LeanLiveTradingService` (LEAN live engine + `CtpBrokerage`). `AddTradingRuntimeLean()` registers both runtime impls (不再注册内置策略——策略由 Scripting 动态加载); it **consumes** (does not register) `ICtpSession` (from `AddCtpInfrastructure`) and `IAnalysisManager` (from `AddQuotesApplication`).
- **`business/Trading.Runtime/Acme.Trading.Scripting`** — 策略动态加载：经 `IStrategyNoteSource` 端口（`Trading.Runtime.Domain`）读策略笔记，按 `StrategyNote.Kind` 分发——`Code`（Roslyn 动态编译 `IStrategy` 实现类源码——装进**可卸载 ALC** + 源码 hash 缓存复用、重加载后 `UnloadStale` 清已删/改名旧版本，见 Non-obvious gotchas「Roslyn 即时编译的程序集资源」）/ `Yaml`（`StrategyProgramYaml` 解析声明式配方 → `YamlStrategy`）→ `StrategyRegistry.Register`。host（Stockapp `StrategyNoteSource`）桥接 `INoteService`，按 `NodeType is CodeStrategy or Strategy` 过滤并映射 `Kind`（CodeStrategy→Code，Strategy→Yaml）——此处是唯一知 NoteNodeType 语义的地方，Trading.Scripting 本身 Notes 无关。`IStrategyScriptingService.LoadAsync()`/`Reload()` + `StrategiesLoaded` 事件（UI 刷新选择器）；订阅 `NotesChanged` → `Reload()` 自动重编译。`Trading.AI` 引用此项目（`CreateStrategyTool` 用 `StrategyScriptCompiler` 即时编译验证；工具创建笔记时设 `NodeType=CodeStrategy`——修前误用 `Note`+`Tags=strategy` 导致不被 `StrategyNoteSource` 加载）——AI 适配器引非 Application business 项目的例外，因编译验证需要。
- **Desktop 回测/实盘页** (`apps/Stockapp/.../ViewModels/TradingViewModel.cs` + `Views/TradingView.axaml`, the `backtest` nav): 回测和实盘**合并为单页**，顶部模式 RadioButton（回测/实盘）切换配置区。子 TabControl（⚙ 配置 / 🎯 策略 / 📈 统计 / 📊 曲线 / 📋 日志）。策略 tab 含策略选择 ComboBox（回测/实盘各自绑 `StrategyName`/`LiveStrategy`）+ 策略参数动态渲染（`StrategyParameterRows`，从 `StrategyRegistry.GetParameterDefinitions` 加载）。配置 tab 含合约/日期/资金/分辨率（回测）/CTP 前置+详细日志（实盘）。日志 tab 按模式显示回测 `LogText` 或实盘 `LiveLog`。互斥守卫（`CanRun`/`CanStartLive` 互相检查）。**策略引擎选择器**（`EngineOptions = {IStrategy, LeanAlgorithm}`）：`IStrategy` 走 CodeStrategy/Strategy 动态加载壳（Lean 中立）；`LeanAlgorithm` 是第三条策略路径——直写 `QCAlgorithm` 子类源码笔记（`NoteNodeType.LeanAlgorithm=8`），经 Stockapp 的 `LeanAlgorithmRegistry`+`ILeanAlgorithmScriptingService`（端口在 `Trading.Runtime.Domain`，Lean 中立；impl 在 `Trading.Runtime.Lean`）Roslyn 编译后复用 Lean 全部能力。VM 经端口注入 `ILeanAlgorithmRuntime`/`ILeanAlgorithmScriptingService`，不直引 Lean 类型；宿主 Stockapp 引 `Trading.Runtime.Lean` 注册 impl（同 `AddTradingRuntimeLean`）。The VM depends on `Trading.Application` + `Trading.Runtime.Domain` + `Trading.Domain` only — 经端口消费 Lean，不直引 `Trading.Runtime.Lean` 类型。
- **AI** (`ai/Trading/Acme.Trading.AI`): `AddTradingTools()` exposes `RunBacktest` + `CreateStrategy`（创建策略笔记 + 即时编译验证，`Confirm` 级）.

Runtime paths:
- **Backtest**: `TradingViewModel.RunCommand` → `Task.Run(() => _backtest.RunAsync(input))` (blocking, so off the UI thread) → `BacktestResult` (12 string stats + `EquityCurve` + `Logs`). **Data caveat**: K-line comes from `IAnalysisManager` (Quotes context, stock-oriented Sina/East/Baidu providers) — futures symbols may have no data; stocks (e.g. `600000`) work.
- **Live**: `StartLiveCommand` → `_live.StartAsync(LiveTradingRunInput)`; preconditions: `ICtpSession` already logged in (CTP connected via the 期货 page) + a complete `MarketDataConnectInput` (md front, built from `CtpConnectorViewModel`). Subscribe to `StatusChanged`/`LogReceived` (dispatch to UI thread). **P1 = signal-only**: `CtpBrokerage.PlaceOrder` logs the intended order and returns `false` — no real CTP order is placed; the tick→bar→signal chain is live. 停止：`Schedule.On(Every 2s)` 检查 `TradingGateway.StopRequested` → `Quit`（无 tick 时 OnData 不调，需 Schedule 兜底）。`AlgorithmStatus.Stopped` 算正常退出（不是 Error）。
- **CtpBar.GetSource**（回测 vs 实盘数据路径的关键设计决策）：回测（`isLiveMode=false`）返回 `LocalFile`（Lean `ShouldStreamSubscription=false` → 走 DataProvider 读 CSV）；实盘（`isLiveMode=true`）返回 `Streaming`（`ShouldStreamSubscription=true` → 走 `IDataQueueHandler.Subscribe` → `CtpBrokerage`）。之前实盘返回 `LocalFile` 导致 `CtpBrokerage.Subscribe` 没被 Lean 调 → `_symbolByInstrument` 空 → tick 全被过滤 → 算法收不到数据。
- **CtpSessionService 增量订阅**：`SubscribeMarketDataAsync` 已连接+同账户时不重建连接，只 `_md.SubscribeMarketDataAsync(新symbols)` 增量累加（native CTP md 支持累加订阅）。之前每次调都 Dispose 旧 _md + new → 实盘订阅覆盖期货页全量。`CtpBrokerage.EnsureCtpMdSubscribed` 不跳过 `_session.IsMdSubscribed`（总是调，CtpSessionService 增量处理）。
- **Lean Config 全局静态 gotcha**：回测和实盘在同进程共享 Lean 的 `Config`/`Globals`/`Composer`（全局静态）。实盘跑后回测需在 `ConfigureLean` 显式覆盖 `live-mode=false` + `Globals.Reset()` + 清 live 残留（`live-mode-brokerage=""`/`data-queue-handler=""`/`data-feed-handler=FileSystemDataFeed`）。互斥守卫防同时跑。
- **P2 (real orders, future) — no new dependency, no cycle.** `CtpBrokerage` already injects `ICtpSession` (uses it for md subscribe / account query / `OrderReceived`+`TradeReceived` events). P2 just makes `PlaceOrder` call `_session.OrderInsertAsync(CtpOrderRequest)` (Lean Order → `CtpOrderRequest` mapping) and translates the already-subscribed `OrderReceived`/`TradeReceived` back into Lean Order/Trade events. This reuses the **same `ICtpSession.OrderInsertAsync`** port the 期货 page manual trading uses (`ICtpTradingService.PlaceOrderAsync`) — two consumers, one port. The edge `Trading.Runtime.Lean → Ctp.Domain` already exists; `Ctp.*` never references `Trading.*`, so there is no cycle. `CtpBrokerage` must stay in `Trading.Runtime.Lean` (it subclasses Lean's `Brokerage`); Ctp stays Lean-free.
- **Swapping the runtime** (Lean→other): implement `IBacktestRuntime`/`ILiveTradingRuntime` in a new project and replace the `AddTradingRuntimeLean()` registration. `Trading.Application`, `Trading.Domain`, and the desktop VM are untouched.

### Workbench shell + theme system

**Workbench engine** (`Acme.Desktop.Workbench`): the shell layout is **data-driven**, not hand-laid in XAML. Each tenant calls `AddWorkbench(WorkspaceDefinition)` declaring its tabs/panels/splitters as a `LayoutSplit`/`LayoutRegion`/`LayoutTabbed` (`LayoutNode` 抽象基类) tree; `WorkbenchShellViewModel` builds nav from the definition. Tenant-specific panels (期货/回测/股票) are injected via `IViewRegistryContributor` (e.g. Stockapp's `StockappViewContributor` registers `FuturesView`/`TradingView`/`StockTradingView`) — the shared shell never references tenant/CTP/Trading types. **Layout persistence**: `LayoutNode` tree serializes splitter positions (incl. chat column width) to `IPreferencesStore`, with drag-writeback + startup restore + a「重置布局」reset (fixes the old chat-width regression where `GridSplitter` positions weren't restored). `PanelKeys` constants directory + `RegionManager` contract hardening prevent the chat-pane-goes-blank regression. Deferred: panel pop-out (P3), plugin system (P4). (`MainViewModelBase` 已拆——239 行、职责单一：shell/账号/业务 VM 组合 + 初始化编排；聊天委托 `ChatWorkspaceViewModel`、导航交 `WorkbenchShellViewModel`、租户页 VM 由租户自持。)

**Theme system** (2 built-in themes + user JSON): `WorkbenchShellViewModel` implements `IThemeHost` (interface in Mvvm; carries `Themes`/`Theme`/`CustomThemeJson`/`IsDark`/`ThemeChanged`/`SelectThemeAsync`). Selecting a theme sets `CustomThemeJson` → `WorkbenchWindow.axaml.cs` subscribes → `ThemeLoader.Apply(window, json)` deserializes the JSON into a `ResourceDictionary` **overlay** on top of `WorkbenchTheme.axaml`+`SharedTheme.axaml` (Color→Brush auto-derivation, symmetric Brush→Color reverse derivation so JSON-edited brushes propagate to Color consumers). Persisted to `preferences.json` key `ui.theme`; restored in `InitializeAsync` before `ActivateAsync` so the window opens already themed. Selection UI: account-menu「🎨 主题」flyout (`MenuItem.ItemsSource`+`ItemTemplate`+`Click` code-behind — NOT `MenuItem.Flyout`, which Avalonia 12 lacks). Built-in themes: `light`/`dark` (each an embedded `Assets/<name>.json`; add one = drop JSON + add to `ThemeLoader.BuiltInThemes` list). User themes: `<tenantDir>/themes/<name>.json` (scanned at startup; `light`/`dark` names reserved).

**Dark native controls** (critical): the JSON overlay covers **only custom token brushes**. Avalonia native controls (TextBox/ComboBox/scrollbars/ListBox/CheckBox/Flyout/AvaloniaEdit TextArea bg) flip via `ThemeVariant`. `ThemeDefinition.Variant` (`"light"`/`"dark"`) → `WorkbenchShellViewModel.IsDarkVariant` → `WorkbenchWindow.axaml.cs.ApplyThemeVariant()` sets `Application.Current.RequestedThemeVariant` (Application-level → all child windows inherit). Every theme JSON carries a `"variant"` field.

**Child-window theming** (`ThemedWindow`): the overlay lands on `WorkbenchWindow` only; child windows (settings/Trace/16 dialogs) would show white blocks in dark mode. Fix = dependency inversion: `IThemeApplier` interface in Shared (`ApplyTheme(StyledElement)`+`ThemeChanged`), `ThemeApplier` impl in Workbench (wraps `ThemeLoader.Apply` + reads `IThemeHost`). `ThemedWindow : Window` base class (Shared) encapsulates ctor-get-applier + subscribe `ThemeChanged` + `OnOpened`→`ApplyTheme` + `OnClosed` unsubscribe — **16 windows inherit it** (`: ThemedWindow`), eliminating 11-line boilerplate each. WorkbenchWindow itself doesn't inherit (it calls `ThemeLoader` directly). Design-time `DesktopApp.Services` null → silently skipped.

**AvaloniaEdit dual palette**: `NotesEditorView.axaml.cs` syntax colors follow the editor's `ActualThemeVariant` — Light+ (blue keywords `#0000FF`/dark-red strings `#A31515`) vs Dark+ (bright-blue `#569CD6`/orange `#CE9178`). `ApplyVscodeColors(def, dark)`/`Load(name, dark)`/`LoadYaml(dark)` all take a `dark` param; subscribes `ActualThemeVariantChanged` → re-applies on live theme switch. YAML `.xshd` cached `_yamlLight`/`_yamlDark`.

**Markdown theming**: `SelectableMarkdownViewer` sets `MarkdownStyleName="Empty"` (NOT GithubLike — GithubLike is hardcoded light + control-level priority that beats app-level theme) and loads a self-contained `MarkdownThemeStyles` providing full markdown styling (table borders/zebra/code block/quote/link) that follows the window theme.

**Skin-pack system (Level-2: 渐变 / aurora 动画 / 每肤 .axaml / 自绘 chrome)** — Level-1 token overlay 之上的 showcase 层，对标 [Codex-Dream-Skin-Themes](https://github.com/aithink001/Codex-Dream-Skin-Themes)（Retro Terminal/Neon Dream 的"炫"）。皮肤包在主题 JSON 上加 4 个 opt-in 字段（全 null/false = 纯 Level-1 主题）：

- **`gradients`** (`Dictionary<string,GradientSpec>`，key 须为 `*Brush` 资源)：把纯色 `*Brush` token 覆盖成 `LinearGradientBrush`（并从首 stop 派生 `*Color`）。`GradientSpec { Type?(string), Angle?(double), Stops[{Color,Offset?}] }`。angle 走 **CSS `linear-gradient`** 约定（0°=↑、顺时针：90°=→、135°=↘）→ 方向向量 `(sinθ, -cosθ)`，StartPoint/EndPoint 居中 ± 半方向（`ThemeLoader.BuildGradient`）。`background.gradient` 把窗口底刷成渐变（优先级 > image > color）。showcase：dream.json 宇宙三停 `#0f0c29→#302b63→#24243e` @135°。
- **`animated`** (`bool?`)：opt-in **aurora 漂移光斑层**。`ThemeDefinition.Animated` → `WorkbenchShellViewModel.IsDreamLayerVisible` → `WorkbenchWindow.DreamLayer`（底层 `Grid`，`IsHitTestVisible=False`，在窗口底之上 / shell `DockPanel` 之下）。`StartAurora` 加 3 颗 `Ellipse` 光斑（`RadialGradientBrush` 中心色→边缘 α0），居中，漂移由 **`DispatcherTimer`（~30fps）tick 直赋 `TranslateTransform.X/Y`**（正弦，X/Y 周期两两互质→轨迹有机不重复）。`StopAurora` Stop timer + 清子控件（隐藏皮肤=0 CPU，不在不可见元素上空转动画）。半透明 `*Brush` 面板（α<FF）让 aurora/渐变透出。**不用 `Animation.RunAsync(TranslateTransform,…)`**——见下方「aurora 动画 cast 坑」。
- **`styles`** (`string?` — `avares://`/文件 URI)：每肤**运行时 `.axaml`** 样式包（Codex-CSS 式特效：`DropShadowEffect` 发光 / 悬停加亮 / 自定义模板）。`ThemeLoader.LoadSkinStyles` 返 `new StyleInclude(uri){Source=uri}` → merge 进 `target.Styles`；`_styleOverlays`(`ConditionalWeakTable<StyledElement,IStyle>`) 跟踪，换肤先移除旧样式再装新。showcase：`Theming/dream.styles.axaml`（紫 `#a78bfa` 发光于 `Border.bubble-user`/`Button.primary`/`Border.card`，`:pointerover` 加亮，`Button.win-btn` chrome 键）。**刻意不用 `<Style.Animations>` 脉冲**（本仓无先例可镜；错路径能编过但运行时静默 no-op，headless 抓不到）——动效由 aurora 层承担。
- **`chrome`** (`ChromeDef { Borderless(bool?), TitleBarHeight(double?) }`)：opt-in **无边框自绘 chrome**（dream 开；light/dark 保留原生）。`WorkbenchShellViewModel.IsBorderless`/`TitleBarHeight`（由 `ApplyChrome(def)` 从 JSON 设，两路径：主题选择 + 实时预览）→ `WorkbenchWindow.axaml.cs.ApplyChrome()` 设 `WindowDecorations = borderless ? BorderOnly : Full`。自绘标题栏 `Border CustomTitleBar`（DockPanel.Dock=Top，`IsVisible={Binding IsBorderless}`，透明底让 aurora/渐变透出）载 min/max/close `Button.win-btn`（codicon `ChromeMinimize`/`ChromeMaximize`/`ChromeRestore`/`ChromeClose`）+ 拖拽（`BeginMoveDrag`）+ 双击最大化。

**Avalonia 12.1.1 chrome/事件 API 坑（重构过——旧名已删）**：`ExtendClientAreaChromeHints` 枚举**不存在**（用 `WindowDecorations` 枚举 `None`/`BorderOnly`/`Full`——`Full` 还原生 chrome）；`SystemDecorations` 标废弃（AVLN5001 → `WindowDecorations`）。`ExtendClientAreaToDecorationsHint` + `ExtendClientAreaTitleBarHeightHint` 仍在，但属 VSCode 式"内容延伸进保留标题栏"模式——全自绘 dream chrome 不用。**无 `StateChanged`/`WindowStateChanged` 事件**——`WindowState` 是 `DirectProperty`，订阅通用 `AvaloniaObject.PropertyChanged` 并过滤 `e.Property == WindowStateProperty` 捕获最大化↔还原（覆盖按钮/双击/OS snap 全路径）。`DoubleTapped` 复用 `TappedEventArgs`（无 `DoubleTappedEventArgs` 类型）。

**AARRGGBB hex 约定（关键）**：Avalonia 把 8 位 hex 解作 **`#AARRGGBB`（alpha 在前——WPF 约定）**，非 CSS 的 `#RRGGBBAA`（alpha 在后）。dream.json 所有半透明面板色用 AARRGGBB（如 `#cc1a1a2e` = A0xcc R0x1a G0x1a B0x2e ≈80% 不透明）。若写 CSS 式 `#1a1a2ecc` 解成 A0x1a（~10% 不透明→面板几近不可见、aurora 透出过度）。由 `ThemeLoaderGradientTests.Translucent_Color_Parses_As_AARRGGBB_AlphaFirst` 锁定。

**aurora 动画 cast 坑（dream 切换闪退根因；2026-08-19 修）**：aurora 漂移**不能**用 `Animation.RunAsync(TranslateTransform, …)`——Avalonia 12.1.1 的 `TransformAnimator.Apply` 把 `Animatable control` cast 成 `Avalonia.Visual`，而 `TranslateTransform` 是 `Animatable` 非 `Visual` → 同步抛 `InvalidCastException: Unable to cast TranslateTransform to Avalonia.Visual`（栈 `TransformAnimator.Apply`→`Animation.Apply`→`Animation.RunAsync`→`RunDrift`→`StartAurora`→`OnVmPropertyChanged[IsDreamLayerVisible]`→`SelectThemeCoreAsync`，EXIT=134 SIGABRT）。`.SafeFireAndForget()` 兜不住——抛在 `RunAsync` 返回 Task **之前**（同步段）。**仅切换崩、启动不崩**：启动期 `SelectThemeCoreAsync` 设 `IsDreamLayerVisible` 在 `DataContext` 订阅前 → `OnVmPropertyChanged` 不触发；`OnOpened` 的 `StartAurora()` 又因 `DreamLayer` 未 realization（`if (layer is null) return`）bail。切换时窗已全渲染、`DreamLayer` 非 null → `StartAurora` → `RunAsync` → 崩。**修复**：漂移改 `DispatcherTimer`（33ms~30fps）tick 直赋 `tf.X = Math.Sin(t*2π/durX)*drift` / `tf.Y = …*0.7`（`Environment.TickCount64` 计秒），`StopAurora` Stop timer + 清子——彻底绕开 `Animation`/animator 选择。同源教训：Avalonia 动画 API「错路径能编过但运行时才抛」（同上述「刻意不用 `<Style.Animations>` 脉冲」），headless 必真触发才抓到；`DispatcherTimer` 直驱是显式可控替代。

### Tenant-specific top-level pages (ContentControl + DataTemplate)

Some nav pages are tenant-specific (Stockapp's 期货 page uses CTP; its 回测/实盘 page uses Trading/Lean; its 股票 page uses StockTrading/FlaUI; Qifu has none). The shared shell must not reference tenant/CTP/Trading types. Pattern:
- Shared `MainViewModelBase` exposes an `object?` content slot + an `IsXxxPage` flag — `Futures`/`IsFuturesPage => CurrentPage == "ctp"`, `Trading`/`IsTradingPage => CurrentPage == "backtest"`, `StockTrade`/`IsStockTradePage => CurrentPage == "stocktrade"`.
- Shared `WorkbenchWindow.axaml` renders each panel via the data-driven `WorkspaceDefinition` + `IViewRegistryContributor` (tenant panels injected, not hard-coded); the `ContentControl`+`DataTemplate` mapping is registered by the tenant `App.axaml` (`<Application.DataTemplates>`: `CtpViewModel→FuturesView`, `TradingViewModel→TradingView`, `StockTradingViewModel→StockTradingView`).
- The tenant VM+View live in the **tenant project** (`apps/Stockapp/.../ViewModels` + `Views`); the tenant `App.axaml` registers `<Application.DataTemplates>` mappings (e.g. `CtpViewModel→FuturesView`, `TradingViewModel→TradingView`, `StockTradingViewModel→StockTradingView`) and the tenant `MainViewModel` assigns the VM to the slot (`Futures = ctpVm; Trading = tradingVm; StockTrade = stockTradingVm;`). Qifu leaves them null (no nav entries, flags stay false).
- The tenant VM depends only on Application-layer services (e.g. `ICtpTradingService`, `IBacktestApplicationService`, `IStockTradingApplicationService`) + the shared connector, never on `externals/Ctp.Net.Core` or `Trading.Runtime.Lean` directly.

### StockTrading context (A股 GUI 自动化下单; distinct from Trading/Lean)

`business/StockTrading` (`Acme.StockTrading.{Domain,Application,Infrastructure}`) is a **separate** context from `business/Trading` (futures backtest/live via Lean). It trades A-shares by **driving the 同花顺 (THS) order client GUI via FlaUI** — NOT an exchange API. Port `IStockBrokerage` (`Domain`, OS/GUI-agnostic: Connect/LaunchClient/PlaceOrder/Cancel/QueryPositions + `IsConnected`/`LogReceived`); `StockTradingApplicationService` (thin proxy) → `IStockTradingApplicationService` (the UI/AI contract). `AddStockTradingApplication()` (cross-platform) + `AddStockTradingFlaUi(opts)` (Windows-only Infrastructure) are the DI entry points.

- **Windows-only Infrastructure**: `Acme.StockTrading.Infrastructure` is `net10.0-windows` + `UseWPF` (FlaUI needs Windows UIAutomation; reading the THS positions grid uses `System.Windows.Clipboard`). Domain/Application stay pure `net10.0`.
- **Avalonia MTA-vs-STA handled**: Avalonia UI thread is MTA; FlaUI/Clipboard need STA. `FlaUiStockBrokerage.RunSta` marshals each op to an STA background thread, so the Avalonia host is fine. csproj `CopyFlaUiDependenciesToOutput` target copies FlaUI transitively-deps into bin (lib projects don't by default).
- **Config port (`IStockTradingOptions` in Domain, peer of `IStockBrokerage`)**: OS-agnostic getter/setter for `ClientExecutablePath`/`ClientWindowTitle`/`StepDelayMs` — lets the UI read/write THS config without depending on the Windows-only `FlaUiStockBrokerageOptions` (Infrastructure). Impl: `FlaUiStockBrokerageOptionsAdapter` (Infrastructure, forwards to the `FlaUiStockBrokerageOptions` DI singleton). **改字段即时生效** — `FlaUiStockBrokerage` holds the same options reference and re-reads per op (no restart needed). Registered in `AddStockTradingFlaUi()` (Windows) / `UnsupportedStockTradingOptions` stub (non-Windows, fields rw but unconsumed). `FlaUiStockBrokerageOptions` defaults: `ClientExecutablePath=null` (attach-only to a running window), `ClientWindowTitle="网上股票交易系统5.0"`, `StepDelayMs=100`.
- **Multi-target host (Stockapp)**: `Acme.Stockapp.Desktop` `TargetFrameworks` is **OS-conditional** — `$([MSBuild]::IsOSPlatform('Windows'))` → `net10.0-windows;net10.0`; otherwise → `net10.0` only. Reason: NuGet restore of a multi-target project evaluates **all** TFMs, so even `dotnet build -f net10.0` would evaluate `net10.0-windows`, pulling in `StockTrading.Infrastructure` (net10.0-windows + UseWPF) → NETSDK1100 on macOS; declaring only `net10.0` on non-Windows keeps the windows TFM out of restore entirely. The Infrastructure `ProjectReference` is `Condition="'$(TargetFramework)' == 'net10.0-windows'"`; `DefineConstants;WINDOWS` marks the windows build. In `App.axaml.cs`, `#if WINDOWS` → `AddStockTradingFlaUi()`; `#else` → register `UnsupportedStockBrokerage` (ops return "仅支持 Windows") + `UnsupportedStockTradingOptions` stubs so the 股票 page + 连接器 still resolve/open on macOS but are inert. Publish must pass `-f` (NETSDK1129: 复数 `TargetFrameworks` 属性即便单值也按跨目标处理) — Windows scripts `-f net10.0-windows`, mac/linux scripts `-f net10.0` (the mac/linux/`build-desktop-macos.sh` scripts all do). **`StockTrading.Infrastructure.csproj` itself is always `net10.0-windows`** (FlaUI/WPF can't downgrade); to let the IDE + `dotnet build Aether.AI.Platform.slnx` load it on non-Windows, it sets `EnableWindowsTargeting=true` Condition `!IsOSPlatform('Windows')` (WindowsDesktop 引用程序集评估；mac 上 Stockapp 走 net10.0 不引用它，这份 windows DLL 不被消费).

### DataQuery context (MySQL 直连 / 任意 SQL 查询工具)

`business/DataQuery` (`Acme.DataQuery.{Domain,Application,Infrastructure}`) 是第一个**直连数据库**上下文——MySQL 直连 + 任意 SQL 查询 AI 工具（含 DDL/DML，非 read-only）。仅供 Qifu 桌面端（手机端不做；单连接）。镜像 Notes 的驱动隔离层化：MySQL 驱动（`MySqlConnector` 2.6.2）隔离在 Infrastructure，经 Domain `ISqlExecutor` 端口；Application 服务驱动无关。

- **Domain**（纯，零 ref）：`DataQueryOptions`（可变 POCO，`Host/Port/User/Password/Database`，Port 默认 `DataQueryDefaults.DefaultPort`=3306，`IsConfigured => Host+User 非空`）+ `DataQueryDefaults`（`CommandTimeoutSec=30`/`MaxRows=500`）+ `ISqlExecutor` 端口（`ExecuteAsync(sql,ct)→SqlRawResult`）+ `SqlRawResult`（`IsResultSet/Columns/Rows/AffectedRows/Error`）。
- **Application**（→Domain）：`ISqlQueryService`→`SqlQueryService`（注入 `ISqlExecutor`，SELECT 结果封顶 `MaxRows`→`Truncated`，映射成 `SqlQueryResult`）。`AddDataQueryApplication()` 注册。
- **Infrastructure**（→Domain + `MySqlConnector`）：`MySqlSqlExecutor`（从 `DataQueryOptions` 建连接串 `Server=...;Port=...;User ID=...;Password=...;Database=...;AllowUserVariables=true;SslMode=Preferred;`；`ExecuteReaderAsync`+`FieldCount>0` 区分结果集（读列+行）vs 非查询（`RecordsAffected`，须先 `CloseAsync()`））。options 不全 → 返回 Error。`AddDataQueryInfrastructure()` 注册 `DataQueryOptions` 单例 + `ISqlExecutor→MySqlSqlExecutor`。
- **配置桥**（镜像 StockTrading「同 options 引用 per-op 重读」）：`DataQueryOptions` 是 Domain 可变 POCO + DI 单例。连接器卡 VM 写它 + 持久化到 `IPreferencesStore`（`mysql.*` keys，跨重启）；`MySqlSqlExecutor` 每次查询现读 options 建连接串 → **改字段即时生效，无需重启**。business 不引 `IPreferencesStore`（桌面 concerns 留在卡 VM）。
- **AI adapter** (`ai/DataQuery/Acme.DataQuery.AI`, mirrors `ai/Notes`): `AddDataQueryTools()` registers `ExecuteSql`（cat "数据查询"，**Dangerous** — 任意 SQL 可 DROP/DELETE/UPDATE 不可逆）。`SqlQueryTool.ExecuteSql([Description] string sql, CancellationToken)` → `ExecuteSqlOutput { Success/IsResultSet/Columns/Rows/RowCount/AffectedRows/Truncated/Error }`。Qifu wires it: `services.AddDataQueryInfrastructure(); services.AddDataQueryApplication(); aether.AddDataQueryTools();`。
- **Qifu 第 4 张连接器卡** (`MySqlConnectorCardViewModel`，镜像 `ThsConnectorViewModel`)：Qifu 前 3 张卡（毓数/mcphub/云文档）是「直接登录」无对话框；MySQL 卡是 Qifu **首张设置对话框卡**。「+」→ `IConnectorSettingsDialogService.ShowSettingsAsync(this)` → `MySqlSettingsWindow`（ThemedWindow 表单 host/port/user/password(PasswordChar)/database +「测试连接」跑 `SELECT 1` close-on-success + 关闭）。`_configured` flag 持久化（用户曾成功测试连接），重启自动重连确认。Qifu 新注册 `IConnectorSettingsDialogService`→`QifuConnectorSettingsDialogService`（`apps/Qifu/.../Hosting/` 新文件夹，switch 卡类型→窗口，镜像 `StockappConnectorSettingsDialogService`）。**Gotcha**：`Acme.Qifu.Desktop.Hosting` 命名空间内 `Application` 被子命名空间 `Acme.Qifu.Application` 遮蔽 → 须写 `Avalonia.Application.Current`（Stockapp 无此冲突因无 `Acme.Stockapp.Application`）。

### AppAutomation context (桌面控制 / 固定过程)

`business/AppAutomation` (`Acme.AppAutomation.{Domain,Application,Infrastructure,StockTradingBridge,McpClient}` — 5 projects, not the usual 3) is the **desktop GUI control** context. It sinks OS-specific GUI automation (FlaUI on Windows, AX/osascript on Mac — future) **out of the Aether process into an out-of-process MCP server** (`externals/FlaUI-MCP`), so Aether upper layers call it via the standard MCP protocol and platform differences = a different `mcp-servers/desktop.json`. Two paths share one MCP server:

- **① 固定过程 (fixed procedures)** — `IProcedureRunner.RunAsync(name, args)` runs a **code-codified UI flow** (deterministic,适合精确/不可逆动作如下单). This is the AppAutomation context's own path.
- **② LLM 直连 (direct)** — an agent calls the desktop MCP server's tools directly (Click/Type/GetUITree) via the existing `McpServerRegistry` (`Aether.AI.Mcp`); the sequence is decided by the LLM at runtime. **Does NOT go through `IDesktopAutomation`.**

> 两条路径在 **server 端**共用同一组工具，但在 **Aether 上层**走**两套独立、互不相连**的客户端 seam：② 用 `McpServerRegistry`（既有 MCP client），① 用 AppAutomation 自己的 `IMcpToolInvoker` 端口。配一份 `desktop.json` 两条都通的前提是 ① 有真实 `IMcpToolInvoker` 实现（`RegistryMcpToolInvoker` 复用 `IMcpServerRegistry` 已连的 desktop server 工具——与专家页 MCP tab 同源，零重复连接）。

Ports (`Acme.AppAutomation.Domain`): `IProcedureRunner` (run a named procedure), `IDesktopAutomation` (C# primitives: Click/Type/GetUITree/FindElement/WaitForElement/GetText…, **只服务于①固定过程**), `IMcpToolInvoker` (CallToolAsync/IsConnected — the seam between AppAutomation and the MCP server; AppAutomation does **not** reference `Aether.AI.Mcp`).

Projects:
- **Application** — `Procedure` (abstract: name + RunAsync(primitives,args)) / `ProcedureCatalog` (name→Procedure) / `ProcedureRunner`. `Ths*Procedure` (ThsConnect/Launch/PlaceOrder/Cancel/QueryPositions/Disconnect) live in Infrastructure (locator-anchored). **DI gotcha**: `AddAppAutomation()` registers each procedure as `Singleton<Procedure>`, but DI only resolves them when `ProcedureRunner` injects `IEnumerable<Procedure>` — its ctor self-registers them into `ProcedureCatalog`. Without that injection the catalog stays empty → `RunAsync` reports「未知固定过程」.
- **Infrastructure** — `McpDesktopAutomation : IDesktopAutomation` (locator↔FlaUI-MCP ref mapping layer: `windows_snapshot` finds ref → `windows_click`/`windows_type`/`windows_get_text`; `FindRefInTree`/`ToChord` pure fns, unit-tested without a server) + `NotConnectedMcpToolInvoker` (Mac/未配 server 桩: `IsConnected=>false`, `CallToolAsync=>"{}"` — 优雅失败「桌面控制后端未连接」, 不崩) + `AddAppAutomation()` DI.
- **McpClient** — `RegistryMcpToolInvoker : IMcpToolInvoker` (复用 `IMcpServerRegistry` 已连的 desktop server, 按工具名从 `GetTools()` 找 `AIFunction` 调 `InvokeAsync`) + `McpDesktopToolInvoker` (独立连备选, 未启用). 隔离 `ModelContextProtocol` alpha 包. **引用 `Aether.AI.Abstractions`**（取 `IMcpServerRegistry`/`McpServerConfig` 稳定契约，零 alpha 依赖）——是 `business/` 引 `Aether.AI.*` 的唯一合法出口（Hosting 的 MCP 契约已上移到 Abstractions，消除原 McpClient→Hosting 的层化违规）.
- **StockTradingBridge** — `AppAutomationStockBrokerage : IStockBrokerage` (maps the StockTrading port → `IProcedureRunner`: Connect/Launch/PlaceOrder/Cancel/QueryPositions → procedures) + `ThsPositionsParser` (持仓 Tab 文本 → `StockPosition[]`). 独立项目, 引 `StockTrading.Domain`（外域契约）+ `AppAutomation.Application`; StockTrading 真正零改动.

**Stockapp host wiring** (`App.axaml.cs`, business-port → host impl pattern, 类比 `IAgentExecutor`): `RoutingStockBrokerage` (host, `apps/Stockapp/.../Hosting/`) is the default `IStockBrokerage` — keyed services hold two backends (`"flaui"` = `FlaUiStockBrokerage`, `"mcp"` = `AppAutomationStockBrokerage`), runtime-switchable via the 股票页 FlaUI/MCP RadioButton (`OrderMethod` enum, persisted `stocktrade.method`); `Active` delegates to the selected backend. Stockapp registers `AddAppAutomation()` + `RegistryMcpToolInvoker` → keyed `"mcp"` `IStockBrokerage` = `AppAutomationStockBrokerage(IProcedureRunner)` + `RoutingStockBrokerage` as default. Non-Windows / no desktop server → `IsConnected` 恒 false, `ProcedureRunner` 优雅失败. The MCP server config template lives at `apps/Stockapp/.../mcp-servers/desktop.json` (copy to tenant dir to enable). **本期不删 FlaUI 多目标**——MCP 路线完全验证通过、决定取代 FlaUI 后才退回单一 `net10.0`（可选后续）.

### Per-agent model + memory (platform layer)

- **Per-agent ModelId**: `AgentDefinition.ModelId` (opaque string) resolved by `IChatClientFactory.Create(modelId)` → `IChatClient`. Platform default (`DefaultChatClientFactory`): uses `AetherAIOptions.OpenAI` key/endpoint. Desktop override (`DesktopChatClientFactory`): maps ModelId = LlmConfig.Id → builds per-provider client.
- **Memory policy**: `AgentDefinition.Memory` (`Full`/`SlidingWindow`/`Off`) + `MaxHistory`. Enforced at agent build time via `HarnessAgentOptions.ChatHistoryProvider`: Full→null (default InMemory), SlidingWindow→`InMemoryChatHistoryProvider` + `SlidingWindowChatReducer`, Off→`NoMemoryChatHistoryProvider`.
- **Extended agent options**: `AgentDefinition` also carries sampling (`TopP`/`MaxOutputTokens`/`ResponseFormat`), HarnessAgent provider toggles (`EnableWebSearch`/`EnableTodoProvider`/`EnableAgentModeProvider`/`EnableFileMemory`/`EnableOpenTelemetry`), `EnableLongTermMemory` (cross-session memory, see [Agent 扩展能力](#agent-扩展能力tools--mcp--skill--长期记忆)), `RequireToolApproval` (per-agent tool-approval master toggle, see [Chat streaming surface](#chat-streaming-surface-reasoning--approval--plan--mode--ask_user)), `ToolApprovals` (per-tool level override `name→"Safe"/"Confirm"/"Dangerous"`), and `Skills` (name list). All mapped in `AgentFactory` (Core enums → MEAI; `ResponseFormat` via a Core `AgentResponseFormat` so MEAI types never leak into Core). Provider toggles default off (lightweight runtime); `EnableFileMemory` only takes effect when `AetherAIOptions.FileMemoryRoot` is set. MCP tools are NOT a flag — they flow through `ToolRegistry` (registered at startup) and are selected per-expert in the editor's MCP section.
- **`AetherAIOptions` paths**: `FileMemoryRoot` (writable root for the file-memory provider; null → silently disabled), `SkillsDirectory`, `PythonExecutable`. Set by the desktop composition root to tenant-data subdirs.
- `HarnessRuntime.Invalidate(agentId)` drops cached agent + definition (on edit).
- **Streaming core reuse**: `HarnessRuntime.RunStreamingCoreAsync` (private static) holds the shared streaming loop. It dispatches every `AIContent` kind in the stream to a `StreamHandlers` callback bundle (Core, framework-agnostic): `OnToken` (answer `TextContent`/`update.Text`), `OnReasoning` (`TextReasoningContent`), `OnToolEvent` (`FunctionCallContent`/`FunctionResultContent` → `ToolStreamEvent`), `OnApprovalRequest` (`ToolApprovalRequestContent`), `OnTodoList` (live `TodoProvider` list after `todos_*`), `OnError` (`ErrorContent`), `OnUsage` (`UsageContent` → token summary). Called by both `RunStreamingAsync(Guid sessionId,…)` (agent path, with AetherSession bookkeeping) and `RunStreamingAsync(AIAgent, FrameworkAgentSession,…)` (workflow path, no bookkeeping). This is how workflows reuse the same display pipeline as agents. See [Chat streaming surface](#chat-streaming-surface-reasoning--approval--plan--mode--ask_user).
- **Workflows** (multi-agent Handoff): `Aether.AI.Workflows` project (peer of Harness, only depends on Core + MAF Workflows NuGet). `WorkflowFactory.BuildAsAIAgent(def, participants, id, name, desc)` → `HandoffWorkflowBuilder` → `.Build()` → `AsAIAgent(InProcessExecution.Default)` → `AIAgent`. The adapter (`CustomWorkflowRunner`) builds participants via `AgentFactory.Create` (same factory as single agents) + maps `CustomAgentDefinition`→`AgentDefinition` via `CustomAgentRunner.ToAgentDefinition` (internal). Chat dispatch: `MainViewModelBase.SelectedWorkflow` (non-null → workflow path; null → agent path), both through the same `RunSegmentedStreamAsync` (run delegate).

### Skills (prompt + Python-script capabilities)

Skills are prompt-based capabilities (Agent Skills spec — same `SKILL.md` format as Claude Code) loaded from a directory and surfaced to the agent via MAF's `AgentSkillsProvider`. **HarnessAgent-only** — `ChatClientAgent` (bare chat) has no skills.

- **Plumbing** (`src/Aether.AI.Harness/Skills/`): `SkillRegistry` (name/description/category/content) + `ISkillRegistryContributor` + `ConfigureSkillRegistry`. Mirrors `ToolRegistry` but for static prompt data (no factory). `LoadFromDirectory(dir)` scans `<dir>/<skill-name>/SKILL.md` (frontmatter `name`/`description`/`category` + Markdown body).
- **Runtime source**: `AgentFactory.ConfigureSkillsProvider` builds an `AgentFileSkillsSource` (MAF) from `AetherAIOptions.SkillsDirectory` — discovers `SKILL.md` + scripts (`.py`/`.sh`/`.js` default) + resources, with a custom `AgentFileSkillScriptRunner` that runs scripts as subprocesses (`python3 <script> <args>`, returns stdout). Per-agent selection via `FilteringAgentSkillsSource` by `AgentDefinition.Skills` (empty = all).
- **Approval disabled by design**: the `AgentSkillsProvider` is built manually and injected via `HarnessAgentOptions.AIContextProviders` (the internal default provider is disabled) with `AgentSkillsProviderOptions.DisableLoadSkillApproval/DisableReadSkillResourceApproval/DisableRunSkillScriptApproval = true`. Chat has no approval UI; without this `run_skill_script` is blocked by MAF's default approval (which `DisableToolAutoApproval` does NOT cover).
- **Skills dir** (desktop): `AetherAIOptions.SkillsDirectory = <tenantDir>/skills`. Drop `<name>/SKILL.md` (+ optional `script.py`) and restart. `SkillRegistry` also scans it to feed the expert-edit skill picker (`ICustomAgentCatalog.GetAvailableSkills`).
- Agent opts in via `Skills` (name list; non-empty = enabled, empty = disabled — no separate toggle), persisted through the custom-agent pipeline (`AgentSourceFields.Skills`).
- `ToolStreamEvent` (tool call/result, paired by `CallId`) lives in `Aether.AI.Core.Agents` — constructed by `HarnessRuntime` from `FunctionCallContent`/`FunctionResultContent` in the stream. Keep it in Core (app/adapter contracts must depend on Core, not Harness internals).

### Agent 扩展能力（tools / MCP / skill / 长期记忆）

Agent 有三种扩展机制 + 跨会话长期记忆，全部在专家编辑器统一勾选/配置。选型：**业务层用 tools，外部用 MCP，流程知识用 skill，结构化参照知识（表 schema / 规则库，需跨流程复用）用 knowledge object**。Token 视角：tools/MCP 每轮带所有工具 schema（随工具数增长）；skill 每轮只带 name/desc 索引，正文 `load_skill` 时才进上下文（按需付费）；knowledge object 同样按需 `read` 才进上下文。

- **Tools**（进程内、强类型）：`ToolRegistry` + 各 `ai/<Context>/Acme.<Context>.AI` adapter 的 `AddXxxTools()` 注册 `AIFunction`，直接调 Application 契约。专家编辑器「内置工具」区按分类平铺勾选 + 权限 ComboBox（Safe/Confirm/Dangerous）。`ask_user` 自动纳入、隐藏在选择器。
- **MCP**（外部、跨进程/跨语言）：`Aether.AI.Mcp` 项目（alpha 包 `Microsoft.Agents.AI.Mcp` 隔离在此，opt-in）。
  - `McpServerRegistry`（`IMcpServerRegistry` in **`Aether.AI.Abstractions`** — the zero-ProjectReference contract package, NOT Hosting）：连接 stdio/HTTP server，预解析工具注册进 `ToolRegistry`（category `MCP`，默认 `Dangerous`，`RegisterMcpTool` TryAdd 防重）。相对命令（`dotnet`/`npx`）经登录 shell 跑（`zsh -lc '<cmd> <args>'`，POSIX 单引号转义）解决 GUI 受限 PATH；绝对路径直接跑。shared-task：`await StartAsync()` 等到连接真正完成（编辑器打开时 `EnsureLoadedAsync` 等它）。
  - 配置：运行时 `<tenantDir>/mcp-servers/*.json`（`McpServerConfigLoader` 兼容主流 `mcpServers` 映射 / 单对象 / 数组；`McpServerConfig.TryParse`/`ToJson` 用 mcpServers 格式，与 Trae/Claude Code/Cursor 互拷）。仓库根 `mcp/` 放自写 MCP server 源码（`mcp/SampleServer` 范例，不引用 Aether）。
  - 管理 UI：Experts 页「MCP工具」tab（`McpViewModel` + `McpView` + `McpServerEditWindow`）—— server 列表 + 连接状态 + 工具清单 + 增删改（单 JSON 文本框）+ 刷新。`IMcpManagementService`（**Abstractions** 接口，impl `McpManagementService` 在 Mcp 项目，写 `mcp-servers/<name>.json` + `RefreshAsync` 重连）。
  - 专家编辑器「MCP工具」区：按 server 分组卡片（名称+状态+错误），工具勾选 + 权限 ComboBox（和内置工具一致，覆盖进 `ToolApprovals`）。
- **Skill**（流程知识 + 轻量脚本）：见 [Skills](#skills-prompt--python-script-capabilities) 节。`run_skill_script` 的 `ParseCliArgs`（`AgentFactory`）兼容数组/对象/整串，并 `StripLeadingPrefix` 剥离 agent 可能带进来的 `python`/`<SQLQ>` 占位符/脚本路径（SKILL.md 的 Bash 写法 `python "<SQLQ>" ...` 与 run_skill_script 的"解释器+脚本已自带"模型不匹配，故剥离）。
- **长期记忆**（跨会话）：`AgentDefinition.EnableLongTermMemory` → `MemoryContextProvider`（Hosting，继承 MAF `AIContextProvider`）经 `ProvideAIContextAsync` 召回 `IMemoryStore` 记忆注入 `AIContext.Instructions`，`StoreAIContextAsync` 沉淀本轮 Q&A 为 `TaskHistory` 记忆项。区别于 `Memory`（会话内聊天历史窗口）。`IMemoryStore`（抽象）+ `SqliteMemoryStore`（`memory.db`）+ InMemory；注入靠 `AgentFactory` 的 `Func<AgentDefinition, AIContextProvider?>` 钩子（Harness 不直接引 Memory，保持解耦）。桌面单用户 → userId=null（全局记忆）。
- **专家编辑器统一 UI**（`ExpertEditView.axaml`）：每个配置块都是 Expander——「内置工具」（`ToolCategories`，按分类平铺 + 权限 ComboBox + 危险标）、「MCP工具」（`McpServerGroups`，按 server 分组卡片 + 权限）、「技能」（`Skills` 平铺勾选）。`GetAvailableTools` 过滤掉 MCP 工具（走 MCP 区）和 `ask_user`（自动纳入）。`ExpertsView.axaml.cs` 打开编辑器前 `await Mcp.EnsureLoadedAsync()` 确保 MCP 连完。

### Rule agent (无 LLM 的规则大脑)

A rule agent is a normal agent whose **brain is swapped from an LLM to deterministic rules** — it reuses the entire agent ecosystem (ToolRegistry / MCP / streaming / approval / ask_user / persistence / skill / long-term memory) and only changes「decide the next step」. The seam is `IChatClient`: `AgentDefinition.Engine == Rule` → `AgentFactory.Create` early-returns `BuildRuleAgent` → `new RuleChatClient(brain).AsHarnessAgent(options)`. Downstream is unchanged — it only reads `AIContent` out of `IChatClient` + `AIFunction` from `ToolRegistry`, doesn't care the brain is rules not an LLM.

- **Model** (`Aether.AI.Core.Agents`): `EngineKind { Llm, Rule }` (default `Llm`) on `AgentDefinition` (+ `Rules` = `RuleProgram` object — carried end-to-end, **never JSON** in the runtime path); `RuleProgram { Name, Steps[], NoMatchReply?, MaxSteps=20, Capture? }`, `RuleStep { Name?, Match, Action }`, `RuleMatch { OnUserRegex?, OnResultRegex?, MinToolCalls?, MaxToolCalls? }` (all-null = always), `RuleAction { Tool?, Args?, ReplyText? }` (`Tool` non-null → stream `FunctionCallContent`, loop continues; `ReplyText` non-null → stream `TextContent`, loop ends; mutually exclusive). `Args` is a `Dictionary<string,object?>` (structured, not a JSON string); `Capture` is a program-level regex whose capture groups feed `{user.N}` to **all** steps (so a step without its own `OnUserRegex` can still reference captured params — multi-step reuse without repeating the regex). The brain substitutes templates **per-value** on the dict (string leaves get `{user}`/`{user.N}`/`{result}` replaced, nested dict/list recurse, non-strings pass through) — paths/quotes/backslashes never break because there is no JSON to escape.
- **Engine** (`Aether.AI.Harness/Agents/`): `IRuleBrain`/`RuleContext` + `RuleProgramBrain` (stateless — each call derives context from `history`: latest user msg, latest `FunctionResultContent`, tool-call count this turn; first matching step's action fires; no match → `NoMatchReply`; `MaxSteps` hard-stop. Guaranteed convergence by design). `RuleChatClient : IChatClient` is the **agent-form** facade (MAF owns the loop). `BuildRuleAgent` reuses `BuildHarnessAgent` line-for-line but **turns off all injection-style providers** (`TodoProvider`/`AgentModeProvider`/skill-load/long-term-memory-recall) — rules can't consume injected NL context; the tool-execution surface (skill scripts, memory store) stays live. (Gotcha: MAF `HarnessAgent` defaults `TodoProvider` on, injecting a 2nd「### Current todo list」user msg that pollutes `BuildContext.LatestUser` — must `DisableTodoProvider=true`.)
- **Two facades, one brain** — rules have **two forms** sharing the same `RuleProgramBrain`:
  - **Agent form** (`RuleChatClient`): a standalone rule agent, summoned to chat like any agent — **zero LLM** the whole way. MAF framework owns the loop.
  - **Tool form** (`RuleToolExecutor` → `run_rule` `AIFunction`, cat「规则」, `Safe`): an LLM agent calls `run_rule(name, input)` once and gets a compact result; the executor runs the tool loop internally and the raw tool results are **hidden from the LLM**. Saves tokens three ways: no decision-reasoning tokens, no raw-result tokens, and business tools stay out of the LLM's tool schema (only `run_rule` is added). `RuleRegistry` dispatches by name; `RuleTool.Create` wraps it. Registered in `AddDesktopCommon` (`ConfigureToolRegistry`).
- **Persistence** — rule agents are a **5th note node type** `NoteNodeType.Rule = 4` (UI「规则」, icon `rule`, amber `#B45309`, `syntax=yaml`; see [Note node types](#note-node-types-5-种-form-节点)). `RuleSourceParser` (`IRuleSourceParser`, `business/Notes/Acme.Notes.Infrastructure/Agents/`, **separate from `AgentSourceParser`**): a **single YAML document** (no front-matter, no `engine` field — engine is hardcoded `"Rule"`). Metadata (name/description/category/tools/toolApprovals/memory/maxHistory/model/requireToolApproval) + program (steps/noMatchReply/maxSteps) coexist at the top level; the program part is serialized into `CustomAgentDefinition.SystemPrompt` and parsed back by `RuleProgramYaml`. Layering: Notes.Infrastructure can't reference Core's `RuleProgram`, so a small step DTO is duplicated (round-trip-identical). `CustomAgentCatalog` dispatches by NodeType: `Agent→IAgentSourceParser`, `Rule→IRuleSourceParser`; `ListAsync` lists both + registers each Rule def's program into `RuleRegistry` (idempotent overwrite) so the same program auto-powers both facades. `CustomAgentDefinition.Engine`/`RulesJson` + `CustomAgentRunner.ToAgentDefinition` map to `AgentDefinition.Engine`/`Rules`.
- **UI** — the Experts page has a **「规则」tab** (`RulesViewModel` + `RulesView`): rule agent cards (list/summon/edit/delete), filtered by `CustomAgentDefinition.NodeType == Rule`. Editing uses an independent `RuleEditViewModel` + `RuleEditView`/`RuleEditWindow` (上下两栏: 上=元数据表单, 下=规则程序 YAML 源码, 与笔记页两栏一致). Rule agents are summoned to chat like normal agents (`ChatTargetKind.Rule`, also routed through `ICustomAgentRunner`); rules have **no plan/execute mode** (`HasModeSupport` false). Cross-VM refresh: `NotesViewModel.NotesChanged` → `Rules.LoadAsync()` too.

### Note node types (5 种 form 节点)

笔记树承载 9 种节点（`NoteNodeType`，`business/Notes/Acme.Notes.Domain`）：`Note=0`（纯文本/markdown）+ 8 种 **form/代码节点**——`Agent=1` / `Workflow=2` / `Knowledge=3` / `Rule=4` / `CodeRule=5` / `CodeStrategy=6` / `Strategy=7` / `LeanAlgorithm=8`。共用 `note_node` 表，差异只在 `node_type` + `content` 编码。`NoteNodeTypeRegistry`（`apps/Acme.Desktop.Mvvm`）集中登记每类的描述符——除显示元数据（UI label / icon / syntax / 新建模板 / 默认内容）外，还带 **3 个能力旗标**：`IsFormNode`（有右栏表单：Agent/Rule/CodeRule/Workflow/Knowledge；策略族/Note=false→全宽代码编辑器）、`HasAgentRunner`（源码直改后失效 `ICustomAgentRunner`：Agent/Rule/CodeRule/Workflow）、`IsChatTarget`（可召唤到聊天：Agent/Rule/CodeRule/Workflow）。新增类型在此加一行带旗标即可，避免散落 switch；未知类型回退 `Note`。两类家族：**agent 家族**（Agent/Rule/CodeRule/Workflow/Knowledge，有 edit-VM+catalog+parser）vs **strategy 家族**（Strategy/CodeStrategy/LeanAlgorithm，无 edit-VM/catalog/parser——Strategy/CodeStrategy 走 `StrategyNoteSource`+`StrategyScriptingService`；`LeanAlgorithm` 直写 `QCAlgorithm` 子类，走 Stockapp 的 `LeanAlgorithmRegistry`+`ILeanAlgorithmScriptingService`，第三条策略路径，未入 `NoteNodeTypeRegistry` 描述符→回退 `Note`）。Form 节点的右栏表单 VM 由 **`INoteNodeEditVmFactory`**（`apps/Desktop/Acme.Desktop.Mvvm/NoteNodeEditVmFactory.cs`）注册表派发——每个 form 类型一个工厂（封装查同级 VM + 建编辑 VM + 接 Save/AutoSave/Cancel 事件，含 CodeRule 的 C# body 回填、Knowledge 的 body 重解析），`NotesEditorView.CreateEditVmForNodeAsync` 经 `DesktopApp.Services` 定位器建字典查表（替代旧 130 行 if 链）。新增 form 类型 = 加描述符行 + 加一个工厂 + 注册。Form 节点在笔记页共用上下两栏布局（上=表单, 下=源码: `ExpertEditView`/`WorkflowEditView`/`KnowledgeEditView`/`RuleEditView`）；纯代码节点编辑器跨满。各 form 节点的持久化 parser 不同（Agent/Workflow/Knowledge 走 `AgentSourceParser`(YAML front-matter+body)/`WorkflowSourceParser`(JSON)/`KnowledgeSourceParser`(YAML front-matter+body)；Rule 走 `RuleSourceParser`(单 YAML 文档)——见 [Rule agent](#rule-agent-无-llm-的规则大脑)）。

### Knowledge objects (知识对象 / 微型知识图谱)

笔记树 4 种 form 节点之一（`NoteNodeType.Knowledge = 3`，UI 显示「知识对象」，强制 `syntax=yaml`、icon `knowledge`；见 [Note node types](#note-node-types-5-种-form-节点)）。**最简通用知识模型**：`KnowledgeObjectDefinition { Kind, Links[], Body }`（`business/Notes/Acme.Notes.Domain/Knowledge/KnowledgeObjectDefinition.cs`），`KnowledgeLink { Role, TargetId?, Target }`。持久化为 YAML front-matter（`kind` + `links`）+ markdown body（`KnowledgeSourceParser`，YamlDotNet，容忍无 front-matter 的老笔记），与 Agent 笔记同构；`name` = 笔记标题（不在内容里）。区别于 Agent（多字段）/ Workflow（JSON）/ Rule（单 YAML 文档）：知识对象只有 3 字段，**typed graph links 是它的定义性特征**——带 role 的图边指向其它笔记，`TargetId` 权威、标题回退（老数据无 id）。

- **AI 消费**（`KnowledgeTool` in `ai/Notes/Acme.Notes.AI/Tools/KnowledgeTool.cs`）：`ListKnowledgeObjects(parentId?)` 列所有/指定 folder 下 Knowledge 节点（body preview 80 字符）；`ReadKnowledgeObject(name)` → `FormatAsync` 拼装成一段 `Definition`：`id:` / `kind:` / `name:` / body + `links:` 段，每个 link 输出 `[role] target (id:真实节点id):` + 目标笔记的**完整原始 Content**（含其自身 front-matter）逐行缩进 2 格。**只展开一层**——子节点自身的 link 不递归（不会无限套娃，也不回拉入口节点）。读是非破坏的、per-flow 的。`CreateKnowledgeObject(name,kind,body,linksJson?,parentId?)` 创建 KO 笔记（`Confirm` 级）；`UpdateKnowledgeObject(name,kind?,body?,linksJson?)` 部分更新（`Confirm` 级）——AI 现在能 CRUD 知识对象，闭环自迭代。
- **DAG 纪律（重要）**：边**单向**，只留「流程 uses/then → 资产」这类正向依赖边；**不要写反向回指边**（`consumed-by` / `schema-for` / `consumes` 等）——它们是冗余、且会被 `FormatAsync` 当噪音内联进 read 产物。分层：**流程层**（`kind=流程`）带 `uses`/`then` 出边，是消费/编排者；**资产层**（`kind=数据源`/`规则`，`links: []` 或只指向同级资产）是被引用的复用目标。
- **复用**：一个资产节点可被多个流程 `uses`。改一处 schema/规则，所有引用它的流程下次 `read` 都拿新版——这是单体 system prompt 做不到的。新场景 = 新建一个流程节点 + 勾选要复用的资产 + 可能加一两个专属规则，不用复制粘贴 prompt。
- **与 Agent 的混合（推荐）**：必须每次遵守的硬契约（输出格式、表范围约束等）留在 agent 节点的 body（system prompt）里确保可靠；重的参照数据（完整字段表、规则库、SQL 模板、示例输出）抽成知识对象按需 `read`。Agent body 里写一句「先用 KnowledgeTool 读『XX流程』」即可。
- **Gotchas**：
  - `NoteTool.CreateNote` 没有 nodeType 参数（只能建 `Note`），但 `KnowledgeTool.CreateKnowledgeObject` 专门建 Knowledge 节点（设 tags/syntax/content）。Knowledge 节点也可经 UI 新建或 `NoteService.CreateAsync(NodeType=...)` 直调。
  - link 靠标题解析时**标题必须唯一**；在 UI 里打开流程节点并保存一次，`KnowledgeEditViewModel.Build()` 会把标题解析成 `TargetId` 落库，之后改名/同名也按 id 精确命中。`KnowledgeTool.ParseLinks`（Create/Update 工具）优先 `targetId`（真实节点 id，按 id 反查标题），回退 `target`（标题解析）——agent 可先用 `ReadKnowledgeObject` 取 target id 再用 `targetId` 建 link（权威，改名不断链）。
  - `FormatAsync` 内联子笔记的 front-matter（含其 links），有轻微噪音但无害；清反向边后已最小化。
- **笔记间内部链接导航**：任意 markdown 笔记正文（含 Knowledge body）可写 `[显示文字](note:目标标题)`（按标题，可读但改名可能断链）或 `[显示文字](note-id:<guid>)`（按 id 权威，改名不断链），点击后 `SelectableMarkdownViewer` 经 `IMarkdownEngine.HyperlinkCommand` 拦截（`NoteLinkHyperlinkCommand`，`SelectableMarkdownViewer.cs`）转发给 `NoteNavigateCommand` → `NotesViewModel.NavigateToNote` 解析前缀 + `FindNoteById`/`FindNoteByTitle` → `SelectAndRevealNode`（展开祖先链 + 设 `SelectedNode`）；非 note: 链接回退系统浏览器。NotesEditorView 标题栏「🔗 插入笔记链接」按钮弹 `TreePickerWindow` 选目标 → 插 `[标题](note-id:<id:N>)`（实现"标题为主显示、存时转 id"）。Knowledge link 行有「→ 跳转」按钮（`JumpToTargetCommand`，用 `SelectedTarget.Id ?? TargetId` 走 note-id）；KnowledgeEditViewModel 经工厂注入 `navigateToNote` 闭包转发 `notes.NavigateToNoteCommand`。

### Chat streaming surface (reasoning / approval / plan / mode / ask_user)

The chat page adapts to HarnessAgent's **full** streaming output. `RunStreamingCoreAsync` branches on every `AIContent` kind (see `StreamHandlers` above); `MainViewModelBase.RunSegmentedStreamAsync` renders each as a `ChatMessageItem` card. All thread through the **same** `RunSegmentedStreamAsync` cooperative loop, so agent + workflow paths both get them. Transcript is grouped into **`ChatTurnItem`**s (`Messages` is `ObservableCollection<ChatTurnItem>`, not flat) — each turn = user request + its agent items under a left-border container with status (Working/Done/Error/AwaitingApproval) + elapsed. Resume reconstructs turns by grouping on user-role messages.

- **Reasoning vs visible text**: `update.Text` concatenates **only `TextContent`** — `TextReasoningContent` (model's private "thinking") is structurally separate and reachable only via `update.Contents`. `NewTextSegment` sets `IsReasoning = isReasoningContent`: only `TextReasoningContent` segments are `IsReasoning=true` → 💭 card (streaming expanded, completed **collapsed** with elapsed, like Claude Code's "Thought for Xs"). `TextContent` segments (the model's **visible narration** between tools + the final answer) are `IsReasoning=false` → rendered as **expanded markdown** text (streaming = live `MarkdownContent` throttled ~6 tokens; frozen = markdown bubble). So only true thinking is collapsed; visible narration/answer are shown — not "everything collapsed". `FinalizeSegment` sets `IsStreaming=false` + `MarkdownContent=Content` on the last `TextContent`.
- **Tool approval — per-tool levels + per-expert override**: tools carry a `ToolApprovalLevel` (in `Aether.AI.Core.Agents`; declared by adapters at `ToolRegistry.Register`): `Safe` (read-only, auto-run), `Confirm` (reversible write, pop dialog), `Dangerous` (irreversible/order/delete/shell, pop dialog + red badge). `AgentFactory` wraps **non-Safe** tools in `ApprovalRequiredAIFunction` when `RequireToolApproval || EnableAgentModeProvider` (i.e. any agent with the mode selector OR explicit approval — so the 4-mode selector can gate them; Safe tools stay unwrapped/inline). The expert author can **override per-tool** via `AgentDefinition.ToolApprovals` (`name→"Safe"/"Confirm"/"Dangerous"`, persisted as `tool_approvals` JSON in `AgentSourceParser`) — `AgentFactory.ResolveApprovalLevel` uses override > declared. The editor tool picker shows a level ComboBox per tool (default = declared) + red/amber badges. MAF approval is a **cooperative re-invocation loop, NOT a callback**: stream emits `ToolApprovalRequestContent` and ends the turn; host re-invokes `RunStreamingAsync` with a `ChatMessage` holding `request.CreateResponse(approved, reason)` (or `CreateAlwaysApproveToolResponse` for "don't ask again") on the **same** `frameworkSession`. `RunStreamingCoreAsync` stashes the original request (`ConditionalWeakTable<FrameworkAgentSession,…>` by `RequestId`); MAF's `ToolApprovalAgent` middleware (default-on) does binding/queuing/standing-rules. `ToolApprovalDecision` (Core DTO) carries the UI decision (`IApprovalDialogService` → `ApprovalDialogService` + `ApprovalWindow`). VM loop: run → if `OnApprovalRequest` fired, `TryAutoApprove(req)` first consults the current chat mode (see [4-mode selector](#chat-4mode-selector-plan--manual--autoedit--auto)) — Auto approves all, AutoEdit approves non-Dangerous, Manual/Plan defer to the dialog → re-run with decision → resumed stream re-emits the approved tool's Call+Result, then the answer. `AutoApprovalRules` can auto-approve/defer but **cannot reject** — reject must go through the loop. Auto-approval reads `SelectedChatMode` **per tool** (live mid-run switching); `!HasModeSupport` (no selector — i.e. `RequireToolApproval`-only agent) always defers to the dialog (legacy behavior). For an agent with neither `RequireToolApproval` nor `EnableAgentModeProvider`, ALL tools auto-run (levels inert).
- **`ask_user` interactive dialog tool**: a host-registered tool (`AddDesktopCommon`, `AskUserTool.AskAsync(AskUserQuestionInput[] questions)` → `IAskUserDialogService` + `AskUserWindow`: a **multi-question form** — each question a section with option buttons + custom text, one 提交 returns all answers as a JSON array in order; user 取消 returns `[]`). `AskUserQuestionInput{Question,Options}` lives in Acme.Desktop.Mvvm (UI-agnostic). `AgentFactory` **auto-includes** `ask_user` in every agent (no per-agent Tools opt-in) and **auto-injects** a system-prompt instruction to use it for confirmations + batch multiple questions in one call (else the agent asks in plain text). It is **hidden from the expert tool picker** (`GetAvailableTools` filters it) — it's always-on infra. Registered as `Safe` → never gated by approval (it IS the interaction UI). Mirrors Claude Code's `AskUserQuestion` (which also takes 1–4 questions per call).
- **Plan UI (📋, reuse `TodoProvider`)**: `EnableTodoProvider` wires MAF's `TodoProvider` (`todos_add`/`todos_complete`/`todos_remove`/`todos_get_*`; items `{Id:int, Title, Description, IsComplete:bool}` — binary, no `in_progress`). After any `todos_*` result, the runtime resolves `agent.GetService<TodoProvider>()` + `GetAllTodosAsync(frameworkSession, ct)` and surfaces the live list via `OnTodoList`. VM renders/updates a 📋 plan card **in the transcript** (pinned to turn top, items[1]); completed items `TextDecorations="Strikethrough"`. `todos_*` calls are **suppressed from the generic tool-card path** (OnToolEvent skips `todos_*`). The plan card is **persisted** as a `PlanUpdated` `AgentEvent` (`todos` JSON payload) — survives restart, rebuilt by `BuildTurnsFromRuns`/`ExpandRun`. Approval (`ItemType="approval"`) cards are runtime-only (skipped in `PersistRunAsync`); `ApprovalState` (0/1/2) drives ⏳/✅/❌.
- **AgentMode plan/execute**: `EnableAgentModeProvider` wires MAF's `AgentModeProvider` (default modes `plan`=interactive / `execute`=autonomous; default mode `plan`). Mode is per-session state (`AgentSessionStateBag`). `HarnessRuntime.GetModeAsync/SetModeAsync` (resolve `agent.GetService<AgentModeProvider>()` + framework session); `RunStreamingAsync` takes a `desiredMode` param applied at run start only (covers new-session-before-first-run; mid-run plan↔execute switch does NOT affect the current turn — by-design, matches Claude Code). `ICustomAgentRunner`/`ICustomWorkflowRunner` thread `GetMode/SetMode` + `desiredMode`. The input-area 4-mode selector (`HasModeSupport` = selected agent's `EnableAgentModeProvider`; set in `OnSelectedAgentItemChanged` **before** the `_isInitializing` guard or it won't show on startup) maps to `desiredMode` via `SelectedChatMode.ToDesiredMode()` ("plan"/"execute"). After each turn `RefreshModeAsync` re-reads the actual mode (catches agent self-`set_mode`) — syncs plan/execute only, preserves the execute sub-mode (Manual/AutoEdit/Auto). A **plan-accept bar** shows only when `HasModeSupport && SelectedChatMode==Plan && !IsAgentRunning && lastTurnHasPlanCard` (signal-triggered, not every plan turn); `AcceptPlanCommand` → `SelectedChatMode=AutoEdit` + `SetModeAsync("execute")` + re-run a continuation turn.

### Chat 4-mode selector (Plan / Manual / AutoEdit / Auto)

The input-area mode selector is a 4-option ComboBox (mirrors Claude Code's Plan/Manual/Edit-automatically/Auto), NOT the old plan/execute ToggleButton. MAF still only stores plan/execute; the 4 modes are VM state — the execute sub-modes (Manual/AutoEdit/Auto) differ only in **per-tool approval gating** done at the VM layer.

| Mode | desiredMode | non-Safe tool approval |
|---|---|---|
| **Plan** | `plan` | defer to dialog (defensive) |
| **Manual** | `execute` | always pop dialog |
| **AutoEdit** (default) | `execute` | auto-approve Confirm; pop Dangerous |
| **Auto** | `execute` | auto-approve all (incl. Dangerous) |

- **VM-layer interception** (`ChatWorkspaceViewModel.TryAutoApprove`): in the `RunSegmentedStreamAsync` cooperative loop, `OnApprovalRequest` reads the current `SelectedChatMode` **per tool** and returns a `ToolApprovalDecision` (Auto→approve all; AutoEdit→query `IToolApprovalLevelLookup.LevelOf(name)`, approve iff `!=Dangerous`; Manual/Plan→null=defer). A non-null auto-decision re-runs via the **same** approval-response path as a user click (no extra LLM call, no approval card inserted — the tool's call+result still render via `OnToolEvent`). `AlwaysApprove:false` (one-shot, mode is mutable so no standing rule). **Live mid-run switching**: changing the mode between approval requests takes effect on the next tool (the reliable part of "mid-run switch"); plan↔execute still applies next-turn (MAF AgentMode isn't reliably mutable mid-run). `!HasModeSupport` (RequireToolApproval-only agent, no selector) always defers to the dialog — preserves legacy behavior.
- **Wrap condition**: `AgentFactory` wraps non-Safe tools when `RequireToolApproval || EnableAgentModeProvider` — so mode-selector agents gate Confirm/Dangerous tools even without `RequireToolApproval`. Safe tools (file edits/read/`ask_user`) are never wrapped → always inline auto-run (agent↔editor closed loop intact).
- **Layering**: `ToolApprovalLevel` + `IToolApprovalLevelLookup` (Core contract) ← `ToolApprovalLevelLookup` (Hosting, forwards `ToolRegistry.LevelOf`), registered in `AddAetherAI`. VM resolves it via `serviceProvider.GetService<IToolApprovalLevelLookup>()` (null → AutoEdit degrades to Manual, safe fallback). `ChatMode` enum in Mvvm; `ChatModeInfo`/`ChatModes.All` (codicon labels) + `ChatModeConverter` (SelectedItem↔enum — Avalonia ComboBox lacks `SelectedValuePath`) in Shared.

### 手机远程控制 agent 回复（进度心跳 + 概览摘要）

手机经 SignalR 远程控制桌面 agent 时**不回传流式过程 token**（老板视角：只要"过程中看进度、跑完收概览"）。桌面 `ChatWorkspaceViewModel.HandleMessageReceived` 跑完 `RunSegmentedStreamAsync` 后不再原样发回 fullText，改为两段：①过程中发**进度心跳**、②跑完发 **LLM 概览摘要**。服务端**零改**——`ChatHub.SendMessage(Guid, string content, string messageType="Text")` 的 `messageType` 是自由 string 透传+持久化，发 `"Progress"` 服务端无需懂语义。

- **进度心跳**：复用 MAF `TodoProvider` 的 `OnTodoList` 回调（桌面计划卡同源）。`RunSegmentedStreamAsync` 加可选尾参 `onRemoteProgress`（本地路径不传=null 行为不变；远程路径传闭包）。回调把 todos 格式化成短文本（`FormatTodosForRemote`：`📋 进度\n✅/⏳ <title>`），经 `IDeviceChatClient.SendMessageAsync(convId, text, "Progress")` 发回手机，fire-and-forget（`.SafeFireAndForget()`——心跳丢失不影响主流程，不 await 避免阻塞流式）。仅对开了 `EnableTodoProvider` 的 agent 有；Rule agent 关所有 provider→无心跳。
- **概览摘要**：新增 `IConversationSummaryService`（`src/Aether.AI.Hosting/ConversationSummaryService.cs`，镜像 `ConversationTitleService`——注入 `IServiceProvider` 懒解析、失败-silent 返回 null、fire-and-forget）。**唯一关键差异**：`factory.Create(modelId)` **传真实 `ExpertItem.ModelId`**（用 agent 同款 LLM，不新增配置），非 title 服务的 null。system prompt 压成 ≤300 字中文概览（要点+结论+关键代码/命令引用不省略、不寒暄）；user 传 fullText 截断 ~8000 字。失败/空→返回 null，调用方退化为截断 fullText（`full[..2000] + …（完整回复见桌面端）`）。
- **退化护栏**：`remoteKind == Rule` → 跳过摘要直发 fullText（`RuleChatClient` 无 LLM）；`WorkflowItem` 无 ModelId → 摘要传 null（宿主默认 LLM）；未开 plan 的普通 agent → 无心跳，只最终摘要（老板至少收结果概览）。
- **手机端 Progress 处理**（`ChatMessage.MessageType` 字段已存在于 `Acme.ChatSocial.Domain`，默认 `"Text"`，服务端 DTO 同名透传，契约层零改）：
  - `GlobalMessageHandler`：Progress 不进未读缓存。
  - `ChatViewModel.OnNewMessage`：Progress 早返回（不动会话列表预览/未读数）。
  - `ChatDetailViewModel.HandleMessageForCurrentConversation`：Progress **覆盖更新**——找同 sender 的进度槽位 `Messages[idx]=fixedMsg`（Replace；ChatMessage 是 POCO 非 ObservableObject，原地改 Content 不刷新 UI 故须 Replace），无槽位则 Add；不进 `_displayedMessageIds`（同 Id 心跳不被拒）、不缓存、不 MarkAsRead。Text（含摘要）到达时先移除同 sender 进度槽位再 Add（收束）。历史加载 3 处过滤 Progress（不残留历史心跳）。
  - `HumanChatMessageTemplateSelector` + `ChatDetailPage.xaml`：Progress 独立模板（muted `Opacity=0.7` 浅气泡 + `ActivityIndicator` + `MarkdownView`），SenderId 判断之前分流。

### Conversation persistence (event-stream model)

Agent 对话持久化是 **typed append-only 事件流**，不是 flat transcript。核心收益：执行轨迹变成 first-class 的 typed 事件，CallId 在 ToolCall/ToolResult 写入时即配对——跨重启重建 LLM 历史与 UI transcript 时，结构不变量（call↔result 配对、role 交替、无孤儿）**由构造保证**，不再需要 restore 净化 saga（旧的 resume-400 `Convert`/`Sanitize` 整段已删）。

- `IConversationStore` (abstraction in `Aether.AI.Memory`) + `SqliteConversationStore` (impl in `Aether.AI.Memory.Sqlite`, opt-in) + `InMemoryConversationStore`. Desktop uses `conversations.db` in tenant dir.
- **数据模型** (`Aether.AI.Core.Conversations.Runs`，纯 record 零依赖)：
  - `AgentRun` = 一次任务执行（用户发送→agent 完成）：`Id`/`ConversationId`/`Seq`/`Status(Running/Completed/Failed/Interrupted)`/`AgentId`/`AgentName`/`ModelId?`/`UserMessage`/`StartedAt`/`FinishedAt?`。`UserMessage` 放 run 上（用户请求属于这次执行）。
  - `AgentEvent` = typed append-only 轨迹：`Id`/`RunId`/`Seq`/`EventType`/`Payload(JSON)`/`CreatedAt`。`EventType` 枚举：`TextChunk`/`ReasoningChunk`/`ToolCall`/`ToolResult`/`PlanUpdated`/`ApprovalRequested`/`ApprovalDecision`/`Error`/`Usage`（`RunCompleted` 刻意不要——`run.Status` 权威）。
  - `AgentEventPayload`（静态类 + nested records）按 type 的 typed JSON：`ToolCall{CallId,Name,Input}`/`ToolResult{CallId,Name,Output}`/`TextChunk{Text}`/`ReasoningChunk{Text}`/`PlanUpdated{Todos}`/`ApprovalRequested{...}`/`ApprovalDecision{...}`/`Error{Message}`/`Usage{Summary}` + `Serialize`/`Deserialize<T>`。复用 `Core.Agents` 的 `TodoItemInfo`。
  - `Conversation` 保留元数据（id/userId/agentId/agentName/title/createdAt/updatedAt + 反范式化 `LastMessagePreview`/`LastMessageAt` 供列表用），**不再挂 `List<Message> Messages`**（已删 `Append`）。`ConversationSummary` 用于历史 flyout。
  - `Message` 类型**保留**——`AetherSession` 内部仍 append `Message.User/Assistant` 做 session 状态（与持久化无关），只是不再作为 transcript 持久化形状。
- **Store API**（`IConversationStore`）：`SaveConversationAsync(Conversation)`（仅元数据）/`GetConversationAsync(Guid)→Conversation?`（仅元数据）/`GetSummariesAsync(userId)`/`FindByUserAsync(userId)`（MemoryService 用）/`DeleteAsync(Guid)`（FK cascade DB 删 + 同步驱逐运行时会话——host 调 `ICustomAgentRunner`/`ICustomWorkflowRunner` 的 `EvictConversation` → `HarnessRuntime.EvictSession` 断强引用，`RestoringChatHistoryProvider` 的 `ConditionalWeakTable` weak-key 缓存随 GC 自动回收，免删后会话残留孤儿）/`AppendRunAsync(AgentRun, IReadOnlyList<AgentEvent>)`（原子 tx：insert run + 批量 insert events + 更新 conversation preview/updatedAt）/`GetRunsAsync(conversationId)`（按 seq）/`GetEventsAsync(runId)`（按 seq）。`SaveAsync`/`GetAsync` 旧名已删（重命名强制编译报错找出所有调用点）。
- **SQLite schema**：`conversation` + `agent_run`(FK cascade→conversation) + `agent_event`(FK cascade→agent_run) 三表。**旧库作废**（不写 flat→event 迁移）：`MigrateAsync` 检测旧 `conversation_message` 表存在 → DROP 全部旧表 → 建新 schema（升级前旧 `conversations.db` 历史会丢失，已知悉）。
- **两条历史路径**（关键分清）：
  - (a) **live 内存路径**——`RestoringChatHistoryProvider._sessionMessages`（`ConditionalWeakTable<AgentSession, List<ChatMessage>>` weak-key——会话被 `EvictSession` 逐出即失强引用、条目随 GC 自动回收）累积 + `StoreChatHistoryAsync`/`FilterMessage` + `SanitizeProviderHistory` + `ToolHistorySanitizingChatClient.SanitizeLive`——**完全不变**（防运行时内存孤儿，与持久化无关）。
  - (b) **跨重启 DB 恢复路径**——`RestoringChatHistoryProvider.ProvideChatHistoryAsync` 首次恢复分支从 `GetRunsAsync`+`GetEventsAsync` + `EventHistoryRebuilder.RebuildLlmHistory` 重建（取代旧 `GetAsync`+`Convert`+`Sanitize`）。
- **`EventHistoryRebuilder.RebuildLlmHistory(runs, eventsByRun)→List<ChatMessage>`** (`Aether.AI.Harness/Agents/`)：按 run.seq+event.seq 重建 MEAI 历史。`User(run.UserMessage)` → `TextChunk` 累积 pendingText → `ToolCall`→`Assistant(TextContent if pending + FunctionCallContent(callId,name,input))` → `ToolResult`→`User(FunctionResultContent(callId, output??"(无返回)"))` → 跳过 ReasoningChunk/PlanUpdated/Approval*/Error/Usage → 尾部 `FlushText`。`DropOrphanToolCalls`：Interrupted run 尾部无 result 的 call 被丢（唯一保留的小 guard，替代旧 `TrimTrailingNonAssistant`）。**CallId 在事件写入时即配对，永不丢→无需合成**。
- **transcript 重建 per-platform**（不在 Harness——因 `ChatTurnItem` 在 Desktop.Mvvm，Harness 不能依赖它，方向错）：桌面 `ChatWorkspaceViewModel.BuildTurnsFromRuns`（tool call+result 按 CallId 合并成一卡）、手机 `AgentChatDetailViewModel.ExpandRun`（tool_call+tool_result 渲染为**两张分离卡**——mobile `ChatMessageItem` 无 CallId，合成 `toolu_mobile_{n}`，call 与配对 result 共享同 id，与 persist 对称）。
- **持久化三路径全走 `AppendRunAsync`**：桌面 `ChatWorkspaceViewModel.PersistRunAsync`（`_nextRunSeq` 跟踪：new=1/resume=max+1；runItems→events 经 `MakeEvent`；plan→PlanUpdated、tool→ToolCall+ToolResult、reasoning→ReasoningChunk、text→TextChunk；approval 卡跳过——runtime-only，与旧一致）。手机 `PersistRunAsync`（seq 从 GetRunsAsync 算 max+1，无字段）。Automation `ConversationBackedAgentExecutor`（get-or-create conv + seq=max+1 + 一个 run+单条 TextChunk event）。
- New chat = lazy create (first send). `ICustomAgentRunner`/`ICustomWorkflowRunner` key runtime sessions by `conversationId` (per-conversation memory isolation); both expose `EvictConversation(Guid)`——删会话时 host 调以断 session 强引用（否则残留孤儿、历史 stale），`ConditionalWeakTable` 缓存随之随 GC 回收。Restart restores display only (agent/workflow context fresh)。
- `IConversationTitleService` (Hosting) — LLM auto-generates title from first turn (fire-and-forget, 4-12 chars).
- `IPreferencesStore` (desktop `JsonPreferencesStore`) — persists selected agent, summoned list, LLM selection, sidebar expand state, + UI layout sizes (window W/H `ui.winW`/`ui.winH`, chat column width `ui.chatW`, notes tree width `notes.treeW`, notes editor/preview row split `notes.previewStar`/`notes.editorStar`, trading config width `trading.configW`). Layout persistence lives in view-layer code-behind (shell VMs stay UI-agnostic) via the `DesktopApp.Services` static locator (set by each tenant `App` after building the container) — see "UI layout persistence" gotcha below.
- **Cross-VM refresh**: `NotesViewModel.NotesChanged` → `Experts.LoadAsync()` + `Workflows.LoadAsync()` (deleting a note that's an agent/workflow refreshes both lists). `WorkflowsViewModel.WorkflowsChanged` → `Notes.LoadAsync()`. Without this, lists are stale until restart. **AI-tool edits**: `INoteService.NotesChanged` event (fired by `NoteService` on Create/Update/Delete) → `NotesViewModel.RefreshAsync` reloads the tree preserving expand-state + selection — so AI-edited notes appear without restart.

- **文档页（Documents）**：VSCode 式「打开项目目录 → 左侧文件树（在 LeftTree 切换层）→ 右侧多标签 AvaloniaEdit 编辑器」，是 AI 编程底座。`DocumentsViewModel` + `DocumentTab` + `FileNode`（UI-agnostic 树模型，VSCode 风文件图标经 `FileIcons`）。md 文件上下分栏预览（镜像 NotesEditorView SplitGrid，眼睛切仅预览/双栏）。项目目录持久化（`docs.projectPath`，重启恢复文件树）；编辑器字体 `docs.editorFontSize`。**文件读 IO 在 VM** `OpenFromDiskAsync`（5MB/二进制检测 + `SyntaxMap` 算语法 → `Open`）。共享 `CodeEditorSetup`（编辑器设置助手：语法高亮/VSCode Light+/Dark+ 双配色/折叠/当前行选中色，按语法 key 字符串）——NotesEditorView 与 DocumentsEditorView 共用。**语法函数单一来源** `SyntaxMap.SyntaxForExtension`（`Mvvm/Syntax/`）——`CodeEditorSetup`（Shared）+ `GitService`（Mvvm）两边转发。

- **层化（镜像 ask_user/BuildTool 模式）**：`ITerminalService` 接口 + DTO 在 `Acme.Desktop.Mvvm`（UI-agnostic，`ITerminalSession`/`TerminalRunResult`/`TerminalSessionItem`）；impl `TerminalService` 在 `Shared/Shell`（能用 Avalonia + RoyalTerminal）；`run_in_terminal` 宿主层工具（同 `BuildTool`/`EditSymbolTool`），在 `DesktopCompositionExtensions` 注册。
- **控件所有权 = view-owns-controls**：`TerminalView` 持 `Dictionary<Guid, TerminalControl>`，每会话一个控件实例。Workbench 用 `BuildTabbed` 预建所有面板视图 + `IsVisible` 切换（不销毁）→ **跨 nav 切换面板常驻、PTY 不断**。`TerminalService`（单例）经 `AttachView`/`DetachView` 持当前 view 引用并转发 Create/Close/SendInput/RunAsync；PTY 独立于渲染，隐藏面板的会话照常跑。`TerminalViewModel`（Mvvm）仅持元数据投影（`ObservableCollection<TerminalSessionItem> Sessions` + `ActiveSession`），订阅 service 事件 diff 重建标签，命令 NewSession/CloseSession/SwitchSession 转发 service。默认 cwd 跟随 `ICurrentProjectDirectoryProvider`（文档页项目目录，镜像 SourceControlViewModel）。
- **shell 解析**：Unix `$SHELL`（回退 `/bin/zsh`→`/bin/bash`）`-l` 交互式登录 shell；Windows `powershell.exe -NoLogo`。主题随 `ActualThemeVariant`（dark `#1E1E1E`/`#D4D4D4`，light `#FFFFFF`/`#1E1E1E`，订阅 `ActualThemeVariantChanged` 重应用）。
- **B2 完成检测 + 退出码 + 捕获（哨兵回显法）**：shell 无关、无需 shell integration 脚本。命令后追加 OSC 8331 自定义序列携带退出码——POSIX `command; printf '\x1b]8331;%d\x07' "$?"` / PowerShell `command; Write-Host -NoNewline "$([char]27)]8331;$LASTEXITCODE$([char]7)"`。`TerminalService.RunAsync` 订阅控件 `DataReceived`，在 lock 下累积 `List<byte>`，`TryFindSentinel` 字节扫描 `ESC ] 8 3 3 1 ; <digits> BEL`（`scanPos` 推进避免重扫），命中 → `ExitCode=解析值`/`Completed=true`/`Output=起点→哨兵间字节`；`TaskCompletionSource<int?>` + `WaitAsync`（linked CT + `CancelAfter(timeoutMs)`）。超时/取消 → `Completed=false` + 已捕获部分输出，**进程继续在面板跑**（用户可观察/Ctrl-C，不重蹈「杀不死→CPU 爆炸」——终端进程归用户掌控）。`ReadCapture` 做轻量 ANSI 剥离（正则去 OSC/CSI/单字符 ESC/`\r`）+ 去首行命令回显。哨兵回显本身是字面 `\x1b` 文本（非原始 0x1B），字节扫描原始 ESC 不会误匹配回显。
- **`run_in_terminal` 工具**（`RunInTerminalTool`，`Shared/Shell`，Dangerous——执行任意命令对齐 `ExecuteShellCommand`）：`RunInTerminal(command, waitForCompletion=true, timeoutMs=null, workingDirectory=null, ct)`。取/建会话（活跃优先，无则建 "agent" 会话并切活跃——用户可见）；`workingDirectory` 非空时前置 `cd <quoted> &&`；`!waitForCompletion` → `SendInput` 即返回；否则 `RunAsync(timeout ?? 180000, ct)` → `Output{Success=Completed&&ExitCode==0, ExitCode, Completed, OutputText, Error, SessionId}`。`Quote()` POSIX 单引号 / Windows 双引号转义。`OutputText` 头尾截断省 token（上限 6000 字符，对齐 Claude Code/Codex 主流做法：长输出截断 + 通知，不搞人话摘要）——失败时 tail 优先（错误/堆栈在末尾，头 10%+尾 90%），成功时均衡（头 20%+尾 80%），截断后附「完整输出在终端面板可见」通知。成败靠 `Success`/`ExitCode`/`Completed`（对齐主流 exit_code 信号），stdout/stderr 混流（PTY 固有，同 Claude Code Bash 合并流）。
- **与 `ExecuteShellCommand`/`get_build_errors`/`run_tests` 的分工**（写进工具 Description 供 agent 选）：`ExecuteShellCommand` 静默管道拿干净 stdout/stderr 做判断；`get_build_errors`/`run_tests` 结构化编译/测试反馈（最干净）；`run_in_terminal` 真实 PTY/全 env/可见可中断，适合需 TTY、长任务想观察/介入、或需完整登录 env 的场景——输出含 VT 噪音（已尽力剥离）不如管道干净。
- **进程生命周期**：关闭会话/窗口 → `ctrl.StopPty()`+`RequestClose()`。Unix `forkpty` session leader 退出通常带走前台组；`dotnet publish` 重子树（MSBuild/csc/node）的孤儿回收是已知验证项（复用 `ProcessKiller` 思路，TerminalView 内联 `StopPty` 兜底）。**取消语义**：agent「结束会话」→ CT → `RunAsync` 返回「已取消」，PTY 进程继续在面板（用户可见可手动停），工具不再独占等待 → 不重蹈管道卡死/CPU 爆炸。
- **注册**（`AddDesktopCommon`）：`services.AddSingleton<ITerminalService, TerminalService>()`（镜像 `IAskUserDialogService`）+ `services.AddTransient<RunInTerminalTool>()` + `aether.ConfigureToolRegistry` 注册 `run_in_terminal`（Dangerous）。`TerminalViewModel` 经 `MainViewModelBase` 构造（同 Documents），不单独注册。两租户 `StockappWorkspace`/`QifuWorkspace` 的 `Panels` 加 `new(PanelKeys.Terminal, PanelKeys.Terminal, "终端", "terminal")`；Layout 树为「左 Vertical-split（上 主 tabbed 去掉 terminal + 下 `LayoutRegion(Terminal)` 220px 可拖）+ 右 chat」（方案 A：终端底部常驻不进 nav）；`IconLoader.CodiconMap["terminal"] = Terminal` + `Codicons.Terminal` 字段（侧边栏 toggle 用）。`CoversSameRegions` 守卫按 DFS 序比 region id——terminal 从 tabbed 移到底部 region 改变序列 → 自动回退代码新布局，无需 bump pref key。
- **底部面板折叠/展开（方案 B toggle + 持久化）**：终端底部 region 可折叠（VSCode 式底部面板开关），折叠时 **PTY 不中断**——仅改 region 的 Grid 行高为 0 + 隐藏其前 GridSplitter + content `IsVisible=false`，会话继续在后台跑。三个入口共享同一 `ITerminalService` 显隐状态：① `TerminalView` 标签条右侧「▼」折叠按钮（code-behind `OnCollapseClick` → `SetPanelVisible(false)`）；② 侧边栏底部终端 toggle 按钮（`WorkbenchWindow.axaml`，绑 `WorkbenchShellViewModel.ToggleTerminalCommand` + `IsTerminalVisible`——可见态 accent 高亮/隐藏态灰，两 Path 按 `IsTerminalVisible` 切显隐）；③ `WorkbenchShellViewModel.ToggleTerminalCommand`（`SetPanelVisible(!IsTerminalVisible)`）。状态流：任一入口调 `TerminalService.SetPanelVisible` → 设 `_isPanelVisible`(lock) + 触发 `PanelVisibilityChanged` 事件 + fire-and-forget 持久化 `ui.terminalVisible`（`IPreferencesStore`，默认可见，仅 `"false"` 折叠）→ `WorkspaceView` 订阅事件（marshal 到 UI 线程）`ApplyTerminalVisibility` 改行高/splitter/content；`WorkbenchShellViewModel` 订阅同事件回写 `IsTerminalVisible`（侧边栏按钮态同步）。`WorkspaceView` 在 `BuildRegion` 记 `_terminalHost`（terminal 的 ContentControl）、`BuildSplit` 记 `_terminalSplitGrid`/`_terminalRow`(=i*2)/`_terminalSplitterRow`(=i*2-1)/`_terminalExpandedHeight`（折叠前记当前展开高度，含用户拖动后实际值）；`OnDataContextChanged` 重建后订阅 + 按 `IsPanelVisible` apply 初始态。`TerminalService` 构造期读 `ui.terminalVisible`（`JsonPreferencesStore.GetAsync` 同步完成，`.GetAwaiter().GetResult()` 安全）。

## Non-obvious gotchas

- **共享 SQLite 基类 `src/Acme.Persistence`**：所有 SQLite-backed store（12 个 business Infrastructure repo + 平台 `SqliteConversationStore`/`SqliteMemoryStore`）继承 `SqliteStoreBase`，不再各自 copy-paste 连接串校验/`ForFile`/`OpenAsync`+busy_timeout/WAL/幂等 lazy schema init/`ExtractDataSourcePath`。基类 API：`static BuildConnectionString(dbPath)`（swap 缝）、`protected OpenAsync(ct)`/同步 `Open()`（busy_timeout=5000 + 可选 `ForeignKeysEnabled`）、`EnsureSchemaAsync(createSql, ct)`/同步 `EnsureSchema(createSql)`（`SemaphoreSlim(1,1)` 阻塞双检 + 建目录 + WAL + createSql + `MigrateAsync`/`Migrate` hook；`_initialized` 仅在「建表+迁移全成功」后置 1、删了 catch-reset——并发首个完成建表，余者拿到锁时见 `_initialized!=0` 直跳过，失败则下次调用重试）、`protected static ExtractDataSourcePath(cs)`。`SqliteMigrations.AddColumn(Async)(conn, table, column, def)` 收拢幂等 ALTER（Notes `icon`/Ctp `auto_login`/Automation 3 列）。**全 async ConfigureAwait(false)**（库最佳实践 + `SqliteLlmConfigRepository` UI 线程 sync-over-async 依赖它不死锁）。新增 SQLite store = `: SqliteStoreBase, IXxx` + ctor `: base(cs)` + `ForFile => new(BuildConnectionString(p))` + `await EnsureSchemaAsync(CreateSql, ct)` + `await OpenAsync(ct)`，迁移进 `MigrateAsync` override。**`Microsoft.Data.Sqlite` 直引只在 `Acme.Persistence.csproj`**——consumer csproj 引 `Acme.Persistence` 即传递获得，删直引。Automation 用同步 `EnsureSchema(CreateSql)`（ctor，#3a）；Qifu 表重建迁移留 `MigrateAsync` override 内联（`PRAGMA table_info` 查 user_id→建新表→复制→换名）。各 repo 的 raw SQL 方言（`INSERT OR REPLACE` 等）仍是 SQLite 方言——swap-aware 非 swap-ready，真换库仍需逐个改 SQL。**不做 EF Core**（CRUD 代码库过度投入）。

- **Roslyn 即时编译的程序集资源（Strategy/Rule/Lean 三套编译器）**：三套即时编译器分处不同层（Strategy=`business/Trading.Runtime/Acme.Trading.Scripting`、Rule=`src/Aether.AI.Harness.Scripting`、Lean 算法=`business/Trading.Runtime/Acme.Trading.Runtime.Lean`），无公共叶子层故不抽共享 helper（层化禁止；本仓「复用模式不复用代码」）。**Strategy + Rule（in-memory 编译）**：旧版 `Assembly.Load(byte[])` 进**默认 ALC 永不卸载也不去重**——每次 `NotesChanged` 全量重编译 → 无界程序集堆积泄漏。修复：源码 SHA256 hash 缓存（`ConcurrentDictionary<hash,(Assembly,CollectibleAlc)>`）命中即复用免重编译；未命中编译进**可卸载 ALC**（`AssemblyLoadContext(isCollectible:true)`，`Load(AssemblyName)=>null` 让共享依赖走默认 ALC → `IStrategy`/`CodeRuleBrain` 类型身份跨 ALC 一致、`IsAssignableFrom` 成立）；重加载后 `UnloadStale(currentHashes)` TryRemove + `Alc.Unload()`（异步——运行中旧实例如回测持有的 IStrategy 保其 ALC 存活到释放，不提前作废；`CreateStrategy` 即时验证 vs `LoadAsync` 全量加载的竞态自愈：被扫走的旧 hash 下次 miss 重编译）。**Lean 算法（落盘 dll）**：Lean `BacktestingSetupHandler` 按路径 `Assembly.LoadFrom` 加载进**默认 ALC**——故 Lean 编译器**留在默认 ALC**（换可卸载 ALC 会与 Lean path-load 类型身份分叉 → 回测断），只能磁盘清理：同 hash 同内容跳过 emit 复用 dll、复用旧 dll 加载失败则删后重 emit 重试、`CleanupStaleDlls` 删本轮集合外的旧 `LeanAlgo_*.dll`。回归测试 `StrategyScriptCompilerCacheTests`（fail-pre 缓存失效→二次编译 Assembly 引用不等 `Assert.Same` 失败 / pass-post 命中缓存引用相等）。

- **CancellationToken 基线 + sync-over-async 卫生**：异步服务接口加 `CancellationToken ct = default` 末参是**默认参、源兼容**（既有调用方不改仍编译），但接口方法加参后所有**实现类**签名必须同步加（interface impl 必须匹配）。CT 只转发到**可取消的 I/O**（`IAppServerHttpClient` 5 方法、HTTP `HttpClient.GetXAsync(url, ct)`、`Task.Delay(ms, ct)`、已有 CT 的 repo）；**本地 SQLite 读不转发**（取消无意义，sub-ms）——`AnalysisManager` 里 `_securityLookup`/`_indicatorCalculator`/`_quoteRepository`、`SecurityClientSyncService` 里 `_securityRepository.AddRangeAsync` 都不转发 ct（注释说明）。MEAI `AIFunctionFactory.Create(method, tool)` 自动绑定运行时 CT（不暴露为 JSON schema 参），故 AI 工具方法加 `CancellationToken cancellationToken = default` 末参即被 agent 运行时取消。**sync-over-async 死锁规则**：UI 线程（`OnFrameworkInitializationCompleted`→`ConfigureServices`→`AddDesktopCommon`）上 `.GetAwaiter().GetResult()`/`.Wait()` 仅在被调 async 已 `ConfigureAwait(false)`、或用 `Task.Run(...)` 包裹（丢 SynchronizationContext）、或被调方同步完成（`Task.FromResult`）时安全。`SqliteLlmConfigRepository` 因被 `DesktopLlmBootstrap` UI 线程 sync-over-async 消费故全方法 `ConfigureAwait(false)`；`SqliteAutomationTaskRepository` ctor 一次性 schema 初始化改用同步 SQLite API（`conn.Open()`/`cmd.ExecuteNonQuery()`）避免 ctor 里 async-over-sync。`JsonPreferencesStore.GetAsync` 是 `Task.FromResult`（同步完成无 I/O）→ 构造期/VM 读 `.GetAwaiter().GetResult()` 安全；`SetAsync` 真异步，UI 线程调必须 `Task.Run(...).Wait()`。
- **ABP auth `scope`**: login MUST send `scope = "Abp alphaagent_chat"` (set in `AddDesktopCommon`). Without it, the token lacks the `Abp` API audience → `401 Bearer error="invalid_token"` on all protected endpoints. Refresh does NOT need scope (refresh token preserves scopes).
- **`TenantHeaderDelegatingHandler`**: registered on `IAppServerHttpClient` ahead of `BearerTokenDelegatingHandler`. Sends `__tenant` header (tenant name from `AppServerOptions.Tenant`). `AppServerOptions` is a **plain singleton** (not `IOptions`), so inject it directly — `IOptions<AppServerOptions>` returns a default empty instance.
- **`APP_BASEURL` 配置**：`AppServerOptions.BaseUrl` 优先级：env `APP_BASEURL` → preferences `app.serverUrl`（从 `<tenantDir>/preferences.json` 读）→ 空。登录窗口有"服务器地址"输入框，登录前 `IAppAuthService.ConfigureBaseUrl(url)` 设置 `HttpClient.BaseAddress` + `AppServerOptions.BaseUrl`，并持久化到 preferences。`DesktopCompositionExtensions` 启动时直接读 preferences JSON 文件（DI 未构建，不能注 IPreferencesStore）。
- **`IAppServerHttpClient.PostAsync<T>` has `where T : class`** — can't use `Guid?`/`bool`. Use `PostRawAsync` + manual parse for value-type responses.
- **`AgentSourceParser.Serialize`** takes a `CustomAgentDefinition` directly (not positional params, not an `AgentSourceFields` type — that no longer exists). Add a new persisted agent field by: extending `CustomAgentDefinition` (Notes Domain) + a parse case in `ParseFrontMatter` (keys are lowercased + underscore-stripped) + the `Serialize` output line + `CustomAgentRunner.ToAgentDefinition` (→ platform `AgentDefinition`) + `AgentDefinition` itself + `ExpertsViewModel` (2 mappings) + `ExpertItem`/`ExpertEditViewModel`/`ExpertEditView.axaml`. List values reuse `ParseListValue` (flow `[a,b]` or block `- a`); maps persist as JSON single-line (see `tool_approvals`). `RequireToolApproval` + `ToolApprovals` (2026-08) are the worked example.
- **File memory read-only crash**: HarnessAgent's file-memory provider defaults to a relative `agent-file-memory` path → `Read-only file system` when launched from a `.app` (CWD=/). Always set `AetherAIOptions.FileMemoryRoot` to a writable dir (desktop: `<tenantDir>/agent-file-memory`); when null, `AgentFactory` silently disables the provider rather than crash.
- **Skill script approval**: MAF's skill tools (`load_skill`/`read_skill_resource`/`run_skill_script`) require approval by default and `DisableToolAutoApproval` does NOT cover them. `AgentFactory.ConfigureSkillsProvider` builds a custom `AgentSkillsProvider` (via `AIContextProviders`, internal default disabled) with approvals off — if you switch back to `HarnessAgentOptions.AgentSkillsSource` (internal provider), `run_skill_script` will be blocked (chat has no approval UI).
- **`.app` PATH**: GUI-launched `.app` has a restricted PATH (缺 `/usr/local/share/dotnet`、`/opt/homebrew/bin` 等); `python3` (skill scripts) / other CLIs may not resolve. Set `AetherAIOptions.PythonExecutable` to an absolute path. **新增任何 spawn 子进程的工具都须套 repo 已有的两套解法模板之一**，否则从 .app 跑必踩「dotnet 不在 PATH」：①**登录 shell**（`McpServerRegistry.ConnectAsync` + `SystemTools/ShellCommandTool`——相对命令包 `$SHELL -l -c '<cmd>'`，`-l` 登录旗 source profile 拿完整 PATH；适用 shell 命令串/管道）；②**绝对路径解析**（`GitService.FindGitExecutable` + `SystemTools/CommandExecutorTool.ResolveCommandPath`——扫 `PATH` env + 常见安装目录兜底，返回绝对路径；适用直进程 no-shell 工具，保 no-shell 契约）。Windows 无此问题（GUI app 继承系统 PATH）。`Environment.CurrentDirectory` 从 .app 也是 `/`（另一坑，工具的 workingDirectory 须由调用方传，如 `GetCurrentProjectDirectory` 工具）。
- **子进程工具的「先杀后读」+ 进程树兜底杀（卡死/CPU 爆炸根因）**：spawn 子进程的工具（`ShellCommandTool`/`CommandExecutorTool`/skill 脚本运行器 `AgentFactory.RunSkillScriptAsync`）超时/取消时**必须先杀进程再读 stdout/stderr**——`ReadToEndAsync` 要等管道 EOF（进程关 stdout）才返回，进程还活着时读 = 永久阻塞 → 死锁卡死（旧 `ShellCommandTool` 超时分支在 finally 杀进程前 `await stdoutTask`，卡死；skill 运行器更甚——`WaitForExit` 之后才读 stdout，输出超 ~64KB 管道缓冲就写阻塞、永不退出）。并发读也要在 `WaitForExit` **之前**启动（同因）。读 `ReadToEndAsync` **不带取消令牌**——取消时应返回残留输出而非抛 OCE 丢数据。进程树杀：.NET `Process.Kill(entireProcessTree:true)` 在 macOS 偶尔漏杀或抛异常（被 `catch{}` 吞掉）→ `dotnet publish` 等重型子树（MSBuild/csc/node）取消/超时后继续吃满 CPU 直到死机。统一走 `ProcessKiller.KillTree`（`ai/SystemTools/.../Tools/ProcessKiller.cs`）：先 `Kill(true)` → Unix 下 `pgrep -P` 递归枚举后代 + P/Invoke `libc.kill(SIGKILL)` 兜底 → `Kill()` 单进程兜底。skill 运行器在 `Aether.AI.Harness`（不能引 SystemTools）内联同语义的 `KillProcessTree`（`Kill(true)`+`Kill()` 兜底，脚本多为单进程够用）+ 120s 超时 + 取消/finally 杀进程（旧版**完全不杀**→孤儿）。

- **TreeView selected text**: Avalonia's default `TreeViewItem:selected` sets accent background but leaves text default-color → unreadable. `NotesTreeView.axaml` adds `<Style Selector="TreeViewItem:selected"><Setter Property="Foreground" Value="White"/></Style>` (scoped via `/template/ ContentPresenter` to avoid bleeding to child rows).
- **Avalonia 12 `CalendarDatePicker.SelectedDate` is `DateTime?`** (not `DateTimeOffset?`). Bind VM date properties as `DateTime?` or you get `InvalidCastException: Could not convert DateTime to Nullable<DateTimeOffset>`. (The 回测 page ran into this.)
- **`Polyline.Points` must never bind to null** — Avalonia builds the geometry on render even when the parent `IsVisible=false`, throwing `ArgumentNullException`. Initialize the points property to an empty list.
- **Securities auto-sync (Stockapp)**: the desktop never used to call `ISecurityClientSyncService.SyncFromServerAsync()`, so `securities.db` was empty → `GetMainFuturesAsync()` returned nothing. Now `CtpViewModel.InitializeAsync` fire-and-forgets an incremental sync on startup + the 期货页 行情 tab has a「同步证券」button. The server endpoint `api/app/security-client-sync/updates` (AllowAnonymous) returns ~5400 securities incl. ~250 futures.
- **Automation (定时任务)**: scheduler is a process-internal 1-min polling `Timer` — fires **only while the app is open** (no cron/Quartz/backfill). Started fire-and-forget from `MainViewModelBase.InitializeAsync` (which parallelizes VM loads via `Task.WhenAll` — Notes/Experts/Automation/Workflows/Rules — with a `volatile _initializing` guard suppressing NotesChanged/WorkflowsChanged/RulesChanged backflow during init; Chat.LoadAsync runs after); `AutomationScheduler.StartAsync` has a double-start guard. Each `AutomationTask` owns a stable `ConversationId` (assigned on create) so all its fires thread into one chat conversation via `ConversationBackedAgentExecutor`. `IAutomationScheduler.TaskCompleted` is subscribed by both `AutomationViewModel` (**local update** — `RefreshTaskAsync(taskId)` fetches the single task via `GetTaskByIdAsync` + updates the matching row in-place via `row.RefreshExecution(task)`, preserving list selection/scroll; NOT a full `LoadAsync()` Clear+re-add) and `MainViewModelBase` (refresh 最近会话). The scheduler calls `IAgentExecutor` (business port) — must be registered at the composition root or DI resolution of `IAutomationService`/`IAutomationScheduler` throws.
- **Fire-and-forget hygiene**: `_ = XxxAsync();` swallows exceptions silently. Use `XxxAsync().SafeFireAndForget()` (`TaskExtensions` in Mvvm — `async void` + `Trace.WriteLine` on catch, no DI dep). 28 call sites unified. Exception: `RoutingStockBrokerage`'s `_prefs?.SetAsync(...)` returns a nullable Task — the extension method is unsafe on null, left as `_ = …`.
